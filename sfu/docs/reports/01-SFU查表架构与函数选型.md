# SFU 查表架构与函数选型

## 一、动机

在 FPGA 上搭一个加速器，旁边通常放一颗控制核，这颗核多半没有浮点单元。
标量的加、减、乘、比较与类型转换可以做成硬件单元直接接上去，
但数学库里的函数是另一类开销：一次 `expf`、`sinf` 或 `cosf` 调用，
在一颗无浮点单元的 32 位软核上约需 2800 到 3300 个周期，`1/sqrtf` 约 600 个周期，
这些数包含测量循环本身的开销，只用于判断量级；同一颗核上一次软件浮点乘法约 131 个周期。
即使基本运算都换成了硬件，多项式或迭代式的数学库实现仍要发出许多条浮点运算，
函数级的延迟不会降到个位数周期。函数级的热点需要函数级的硬件原语。

这里的 SFU（special function unit，特殊函数单元）是四个这样的原语：
指数 `exp`，正弦 `sin`，余弦 `cos`，平方根倒数 `rsqrt`，即 `1/sqrt(x)`。
C 数学库函数名末尾的 `f` 表示单精度 `float`，四个单元的输入与输出都是 IEEE-754 binary32，
下文记作 FP32。

四个函数在推理与渲染负载中的调用点各不相同。指数出现在 softmax、SiLU 激活与透明度衰减里；
正弦余弦出现在旋转位置编码与姿态计算里；平方根倒数出现在均方根归一化与向量、协方差的归一化里。

这些调用点给出两种调用方式。一种是阻塞式：调用方发出一条请求后停下来等结果，
一次只有一条请求在单元里，此时单元延迟就是这次调用的价格。
另一种是流水式：调用方每拍发起一条，前一条的结果还没出来，下一条已经进去，
此时发起间隔比单条延迟更重要。四个单元必须同时适配这两种方式，
所以要求是：定长流水，每拍可以发起一条，单元延迟压到能满足时序的最小值。

不是所有数学函数都值得做成硬件。选取的条件有三条：动态调用多，输入在运行时变化，
不能由已有原语廉价组合。`sqrt(x)` 可以写成 `x · rsqrt(x)`，不需要再放一套开方硬件。
旋转位置编码里 `powf(10000, k/d)` 只依赖少数几个常数指数，可以预先算好。
softmax 的减最大值、求和与缩放可以由比较、加法与乘法组成。
`tan`、`log` 等函数不在这些负载的主路径上。先把能在软件里静态折叠的工作折叠掉，
再为剩下的高频动态工作造硬件。

## 二、为什么是这几步

硬件实现超越函数通常有三条路线。

迭代计算，例如 CORDIC，逐轮增加精度，N 位精度大约需要 N 轮；
不完全展开时，延迟与发起间隔都受迭代次数限制。

多项式逼近可以得到较高精度，但五到七阶的霍纳求值需要串联多个乘加，
还要处理定义域归约、舍入与特殊值。

查找表把输入折叠到一个小区间，用区间内的位置寻址片上 ROM。
主要成本是 BRAM、地址生成与定义域还原，数据通路固定，延迟确定。

SFU 选择查找表。由此需要确定的是四个函数共用的骨架，一共七件事：

1. **统一结构。** 四个函数的压缩与还原各不相同，但要落进同一个"压缩、查表、还原"的形状里，
   还原只动 FP32 的阶码或符号字段，避免在表后再放一条浮点乘法链。
2. **表的规格。** 表多大、存什么格式，决定 BRAM 用量与精度量级。
3. **流水骨架。** valid 链、`flush`、数据寄存器与出口寄存器的写法，决定单元能否每拍发起一条。
4. **延迟常数。** 调用方要按延迟搭建对齐流水，延迟必须有唯一定义处，并且是实测量。
5. **数值契约。** 特殊值、denormal、NaN 的语义要四个单元一致，并与同一数据通路里的
   FP32 算术单元一致。
6. **表的生成与加载检查。** 表是网表的一部分，必须能从公式重建；
   表没加载时综合与仿真都不报错，必须另设检查。
7. **验证分层。** 行为是否变化、数学上是否合格、表是否被加载，由不同的判据分别回答。

前两件决定电路长什么样，第三、四件决定它能被怎样调用，后三件决定它的行为能不能被说清楚、
被检查。少了任何一件，四个单元都会各自长出一套写法。

## 三、每一步做了什么

### 3.1 统一结构

四个函数统一拆成三步：

1. **定义域压缩。** 用字段拆分、移位、加法与常数乘法把输入映射到有界区间，
   同时保存整数阶码、象限或阶码增量。
2. **查找表。** 用 10 位地址读取 1024 × 32 的同步 ROM。
3. **结果还原。** 把保存的信息加回表项，组装 FP32 输出。

```text
                          ┌─ exp：整数 n ─────────────────────┐
FP32 输入 ─> 定义域压缩 ──┼─ sin/cos：象限与结果符号 ─────────┤
                          └─ rsqrt：阶码增量 k ───────────────┤
                                   │                         │
                                   └─ 10 位地址 ─> 1024×32 ROM │
                                                        │    │
                                         表项 + 保存字段 ┴────┴─> FP32 输出
```

三类还原都落在阶码或符号字段上：指数把 `n` 加进阶码，正弦余弦替换符号位，
平方根倒数把 `k` 加进阶码。每个函数的压缩方法见第 02 到 04 章。

### 3.2 表的规格

每张表 1024 项，每项 32 位，共 32,768 位。Artix-7 的一块 RAMB36 提供 36,864 位，
能容纳一张表；下一档 2048 × 32 需要两块。1024 项是 BRAM 数量跳变之前的最大二次幂深度。

表项存完整的 FP32 位图，不存自定义定点数。还原时直接复用表项的符号、阶码与尾数字段，
省去格式转换逻辑。

不做线性插值，省掉一组乘加。10 位索引的区间宽度约为 `2^-10`，
但这个数不能直接当作所有函数的误差：正弦余弦看绝对误差，指数与平方根倒数看相对误差，
各表的取样点（区间左端点、中点或闭区间）也不同，最终精度以对 RTL 输出的独立测量为准。

表结构是一个共用模块 `bram_lut_1024x32`：同步读、无读使能，
`(* ram_style = "block" *)` 强制推断为块 RAM，初值由参数 `Memfile` 指定的文件经
`$readmemh` 读入。表地址由组合逻辑直连 BRAM 的地址口，BRAM 自带一级地址锁存，
不在外部再寄存一次。

查找表并不意味着不用 DSP：它替代的是函数主体，定义域压缩里的常数乘法仍然存在。
指数的常数乘法映射为 2 个 DSP48，正弦余弦的相位乘法映射为 4 个 DSP48，平方根倒数不用 DSP。

### 3.3 流水骨架

四个函数单元采用同一套写法：

- valid 链单独一个过程块，驱动 `out_valid`；
- `flush` 只出现在 valid 链那一个块里，全模块没有第二处；
- 数据寄存器一律无条件推进，不做 valid 门控；
- 出口寄存器由末级 valid 门控。

作废一条在飞运算等于让它的 valid 位消失，数据继续往下走，
`out_valid` 为低时 `out_data` 没有意义。

同步读 BRAM 的读延迟用一级与读操作并行的寄存器对齐：地址被采样的那一拍，
控制字段同时进入这一级寄存器，下一拍与表数据一起到达。

### 3.4 延迟定义与延迟常数

单元延迟定义为：`in_valid` 被采样的时钟沿记为 T，`out_valid` 拉高的时钟沿为 T+N。

`sfu_lat.vh` 是四个延迟的唯一定义处，各值是仿真实测量，不由流水级数推算。
单元测试台断言实测值等于宏值：修改流水级数后，先跑测试台取实测值，再更新头文件。

延迟同时是模块之间的接口约定。调用方直接例化某个单元并为其他信号搭建等深的对齐流水时，
错一拍就是数据错位，属于功能错误，与数值精度无关。所以调用方必须引用宏，不得另写数值。

### 3.5 数值契约

四个单元的特殊值语义统一如下：

- 输入采用 DAZ：指数字段为 0 的位图按同符号零解释。这与 FTZ 语义的 FP32 算术单元
  对同一个位图的解释相同。
- 所有 NaN 输出为规范 qNaN `0x7FC00000`：不透传输入尾数，不保留符号位，sNaN 在此静默。
- 结果是近似值，不做正确舍入，不产生异常标志。

每个函数的完整契约表与精度预算列在模块手册中。精度预算是规格的一部分：
指数相对误差 4e-4，正弦余弦绝对误差 1.6e-3，平方根倒数相对误差 5e-4。
改动后达不到预算时应当修改算子，而不是放宽预算。

### 3.6 表的生成与加载检查

四张表由 `gen_luts.py` 从公式确定性生成，表的取样口径以生成器为准：
表项先按 binary64 求值，再按 IEEE-754 就近舍入收成 FP32，文本为小写 8 位十六进制、LF 换行，
重复运行逐字节相同。`--write` 写表，`--check` 只校验。

生成器同时写出两份 manifest：JSON 一份供人和脚本读，Tcl 一份供综合前检查读，
两份都记录每张表的项数、首项、末项与 SHA-256。

表加载失败时两侧都不报错，所以两侧各设检查：

- 综合前，`check_sfu_luts.tcl` 核对表存在、项数、首末项与 SHA-256，不符即报错退出；
- 仿真时，单元测试台检查结果中不含 X；
- 两侧共同，`gen_luts.py --check` 核对表与 manifest 逐字节等于生成器输出。

SHA-256 由 Vivado 自带 Tcl 环境中的 `sha256` 包计算，不依赖操作系统命令。

### 3.7 验证分层

判据分成五层，每层回答一个问题：

- 发起形态：单元测试台用 hold、pulse、每拍一条等多种驱动跑同一组输入，
  回答结果是否与调用方式无关、延迟是否等于宏；
- 冻结参考：9500 条固定激励与冻结的输出逐位比较，回答行为有没有变；
- 独立参考：`verify_sfu.py` 按 libm 计算误差上限并逐条查特殊值，回答行为在数学上是否合格；
- 表可复现：`gen_luts.py --check`，回答表是否等于公式；
- 综合快照：离线综合数网表单元并检查每块 ROM 带初值，回答资源、时序与表加载。

冻结参考与独立参考不能互相替代。冻结参考由 RTL 自身的输出冻结而来，
对产生它的那次改动没有判断力；有意改变行为时，先由独立参考确认新行为合格，再重新冻结。

## 四、遇到的问题

### 4.1 第一版查表实现被判定为精度不足

第一现场。四个函数的第一版查表实现，单独测试时每个函数一万余条随机向量全部通过，
但在语言模型推理中输出乱码。当时的归档结论是：

```text
每个函数单独测试都正确（10000+ 随机向量 PASS），但 RTL 是自研查表方案，
与软件浮点差 1 到 2 个最低位单位的系统性算法差异；在多轮推理中逐层累积，
约第 9 个 token 使 softmax 的指数输入漂出范围，产生非数，输出乱码。
这不是缺陷，是架构性精度问题，留待用多项式替代查表从根源解决。
```

解读。这个结论若成立，查表路线就走不通，需要改为多项式逼近；若不成立，改用多项式是白绕一圈。
所以在重写任何硬件之前，需要先回答：那次崩溃是否由精度造成。

定位。要判定崩溃是否与精度有关，需要把精度作为唯一变量控制起来。
把推理程序移到工作站上运行，在四个函数的调用处各插一层包装，可以把结果降低到指定的尾数位数。
先确认这个环境本身不走样：不降精度时输出完整通顺，与原平台一致。然后逐档降低精度：

| 误差模型 | 贪心解码 | 采样解码 |
|---|---|---|
| 就近舍入到 8 位尾数 | 与精确基线逐字符一致 | 与精确基线逐字符一致 |
| 就近舍入到 4 位尾数 | 输出连贯 | 未测 |
| 就近舍入到 3 位尾数 | 内容漂移，仍然通顺 | 未测 |
| 单向截断到 6 位尾数 | 输出连贯 | 轻微漂移，仍然连贯 |

8 位尾数对应约 4e-3 的相对误差，比查表方案的 1e-3 量级还宽，输出仍然逐字符一致。
这个负载对超越函数的精度很不敏感，"差 1 到 2 个最低位单位逐层累积"解释不了崩溃。

接着把第一版硬件的指数函数逐位翻译成 C，接进同一个环境，输出退化为乱码：

```text
Once upon a time, there was a little girly ... rourowd eldieldivelieldive
```

同一个环境、同一份权重，唯一的变量是指数函数的实现。6 位单向截断的最大误差 1.5e-2，
输出连贯；第一版硬件在零点附近的误差只有 6.8e-4，却产生乱码。
差别不在误差的幅度，在误差的形状：第一版在大部分定义域上给出与正确答案无关的结果，
具体见第 02 到 04 章各自的第一个问题。

根因与修法。四个函数是同一种问题：各自只做了有限范围的归约，逻辑只在一条窄带上成立。
而测试全部通过的原因在测试的构造方式：期望值由一个脚本生成，这个脚本是同一套硬件算法的
逐位复制品；随机激励又恰好落在各自正确的那条窄带里。

验证方式因此改了三条：期望值一律由 libm 生成，不再由算法的复制品生成；
激励覆盖整个定义域，包含各自的极端值；每个函数都用第一版跑一遍同一套测试，
确认测试会大面积失败：平方根倒数 49.9% 失败，指数 81% 失败，正弦 97% 失败。
第三条是前两条的验收条件：一套测试只有在对已知错误的版本失败时，它的通过才有意义。

原判据为什么没有覆盖到它：期望值与被测对象同源，这类测试的通过率与被测对象是否正确无关。

### 4.2 延迟表与实测不符

第一现场。准备删除一级多余寄存器时，先逐个实测了单元延迟，与文档与头注释对账：

```text
单元         文档或头注释写的   实测
exp          3 拍               4 拍（第 02 章切级之后变为 6 拍，文档仍未改）
sin / cos    未单列             单元 2 拍，外层包装另加 1 级寄存器，端口上测得 3 拍
rsqrt        4 拍               5 拍
```

以上为按当时的对账记录还原。

解读。三个单元的延迟没有一个与文字记录一致，而且错得没有规律：
有的是流水级数改了文档没跟着改，有的是模块外面包了一级"延迟对齐"寄存器，
使单元端口上的延迟与调用方看到的延迟不同。

定位。表之所以错，是因为没有任何东西在检查它。延迟只写在文字里，改流水级数的人
不会想起去改文字；外层那一级寄存器与同一文件头注释里写的"各子单元独立，不做延迟对齐"自相矛盾。

根因与修法。三件事一起做：新建 `sfu_lat.vh` 作为延迟的唯一定义处，值取实测量；
单元测试台断言实测值等于宏值，断言方向是"实测必须等于宏"，反过来写会自动接受任何改动；
删除外层那一级对齐寄存器，让单元端口上的延迟就是单元延迟。

原判据为什么没有覆盖到它：延迟是文字记录，没有测试台测量过它。

### 4.3 两种流水写法并存

第一现场。统一骨架之前，四个单元的写法如下：

| 单元 | 数据寄存器推进 | 出口寄存器 |
|---|---|---|
| 指数 | 无条件，唯独第一级由 `in_valid` 门控 | 由末级 valid 门控 |
| 平方根倒数 | 无条件 | 由末级 valid 门控 |
| 正弦 | 由 `flush` 门控 | 每拍更新 |
| 余弦 | 由 `flush` 门控 | 每拍更新 |

解读。两种写法各自都是对的，但同一个目录里并存两套，读代码的人必须逐个模块确认一遍。

更要紧的是数据寄存器的 valid 门控。被延迟版 valid 门控的数据寄存器隐含两条要求：
输入保持至少两拍，同时只有一条运算在飞。阻塞式调用方恰好满足这两条，
每拍发起一条的调用方两条都不满足。平方根倒数与指数的收表级都因此在连续发起时出过错，
见第 02 章 4.3 节与第 04 章 4.2 节。

定位。指数第一级的门控用的是 `in_valid` 本身而不是它的延迟版：第一级寄存器与 valid 链同拍推进，
气泡期间采到的旧值对应的 valid 为低，出口读不到。这个写法是安全的。

根因与修法。统一为 3.3 节的四条约定。指数第一级那处门控也删掉，
原因是它与真正的缺陷形状完全一样，留着它，下一个读代码的人必须逐拍推演才能分辨哪个安全。
修改前后 9500 条固定激励逐位不变。

原判据为什么没有覆盖到它：写法是否统一不影响功能，没有判据指向它；
而隐含的保持两拍与单条在飞的要求，只有用连续发起的驱动才能暴露。

### 4.4 flush 的判据放在了集成层

第一现场。统一骨架时 `flush` 只保留在 valid 链里，需要确认作废语义没变。
集成层已有一个专门检查作废的测试台。把正弦单元的 valid 链改成完全不响应 `flush`，
再跑那个测试台（测试台名属于集成方，此处略去）：

```text
42 PASS, 0 FAIL
```

解读。注入确实让正弦单元在 `flush` 之后仍会给出结果，集成层的判据却一条都没有报错。

定位。注入不报错有两种可能：判据无效，或者那条路径在当前配置下不可达。
这次是后者。集成层自己有三道独立的作废拦截：出口选择寄存器、在飞标志与应答寄存器，
`flush` 时各自被清一次，单元内部的 `flush` 是冗余的第四道。
单元的结果即使漏出来，也到不了应答口。

根因与修法。判据移到单元端口上：发起一条，在它还在流水线里时拉一拍 `flush`，
此后不许再出现任何 `out_valid`。三个单元各一条，即 `tb_sfu_stream.v` 的 X10。同一处注入再跑一次：

```text
  PASS  X10 exp  flush kills in-flight op (no out_valid after)
  FAIL  X10 sin  flush kills in-flight op (no out_valid after)
  PASS  X10 cos  flush kills in-flight op (no out_valid after)
      leaked out_valid: exp=0 sin=1 cos=0
```

原判据为什么没有覆盖到它：判据放得比被测对象高一层，中间每多一道冗余保护，
它对下层缺陷的分辨率就低一档。

### 4.5 表没有生成器，加载失败不报错

第一现场。四张表以数据文件的形式存在，没有生成器，舍入过程无法审计。
表结构模块的头注释里写着加载失败的后果：

```text
路径不对时综合只给一条 CRITICAL WARNING，随后产出一块无初值的 ROM
```

仿真侧同样不报错：表找不到时整块 ROM 读出 X，而 `X === X` 为真。

解读。表是网表的一部分，却既不能从公式重建，也没有检查保证综合时真的读到了它。
一块无初值的 ROM 会让整条读通路被优化成常量，BRAM 用量不涨，不专门核对资源报告就看不出异常。

定位。仿真侧已有检查：单元测试台断言结果不含 X。缺的是综合侧的检查与表的生成器。

根因与修法。新增 `gen_luts.py` 与两份 manifest，新增综合前检查 `check_sfu_luts.tcl`，即 3.6 节。
验收判据是生成器必须能重现当时在用的表：正弦表与两张平方根倒数表重新生成后逐字节相同，
这回答了一个此前无法回答的问题，即这些表当年是否按它们声称的公式制成；
指数表在同一轮按第 02 章 4.5 节有意改为中点取样。

两侧检查的有效性用注入验证。截断指数表的最后一项，综合前检查报错退出：

```text
SFU LUT preflight: exp_lut.mem has 1023 words, expected 1024
```

仿真工作目录里不放正弦表，`tb_sfu_stream.v` 报错：

```text
  FAIL  sin X3 no X in results (.mem really loaded)
  FAIL  cos X3 no X in results (.mem really loaded)
  FAIL  X7 cos(0.0) == 1.0 exactly
  FAIL  X9 sin_lut.mem[1023] == 1.0 exactly (cos_func has no zero bypass)
 SUMMARY 4 FAIL / 22 checks
```

不放两张平方根倒数表，`tb_rsqrt_stream.v` 的 R5 与依赖数值的 R1、R4、R7、R11b 一起报错。

原判据为什么没有覆盖到它：综合流程只把加载失败当作警告，没有任何一步把它升级为错误。

### 4.6 冻结参考对产生它的改动没有判断力

第一现场。第 02 章 4.5 节修改指数表时，冻结参考 `golden_ref.txt` 必须重新冻结，
否则每条指数结果都与旧参考不同。重新冻结之后，所有逐位对拍判据都通过。
同一轮，调用方自己的误差测试把指数的阈值定在 1.5e-3，那是为旧的左端点表留的余量。

解读。重新冻结的参考来自修改后的电路自身，它对这次修改是否正确没有任何判断力：
如果当时只把常数改回数学值（平均误差增加 60%）并重新冻结，逐位对拍同样全部通过。
而误差测试的阈值没有随误差减半而收紧，余量变成了 4.6 倍，把旧表换回去它照样通过。

根因与修法。修改行为的那一轮，正确性由独立参考 `verify_sfu.py` 承担：
它按 libm 计算误差并检查预算，按契约逐条检查特殊值，不读 RTL，不依赖冻结参考。
冻结参考的作用从下一次改动起才恢复。误差阈值按实测收紧到约 2 倍余量。

原判据为什么没有覆盖到它：冻结参考只能回答"变没变"，不能回答"对不对"；
阈值的余量没有跟着被测量走，判据就退化成摆设。

### 4.7 NaN 与符号零有两套语义

第一现场。9500 条固定激励中的 NaN 输入，四个单元的输出分成两组：
指数与平方根倒数原样透传输入的位图，sNaN 进 sNaN 出；正弦与余弦输出规范 qNaN `0x7FC00000`。

解读。四个单元对同一个输入给出两种语义，使用者必须逐单元记住差别。

根因与修法。统一为规范 qNaN，即 3.5 节。极小正规数的符号零问题是同一次契约复核中查出的，
见第 03 章 4.5 节。契约表同时增加"极小正规数"一行，因为这类输入既不属于 denormal，
也不属于零。

原判据为什么没有覆盖到它：独立参考当时只按每个单元各自的旧语义检查，没有一份统一的契约表作依据。
