# FP32 乘累加反馈环的启动间隔

> **本章的结论已被[第十章](10-FP32乘累加换成定点窗口累加器.md)取代，保留为历史记录。**
> 这一章讲的是"三拍的反馈环导致喂积间隔必须是 4，于是摆 4 个累加器交错把它压回 1"。
> 第十章把反馈环本身压到了一拍，交错累加器、归约树、以及本章推导出来的
> `FP32_MAC_PACE = FP32_ADD_LAT + 1` 一并撤除。
> 本章讲的"反馈把延迟变成依赖距离"那套分析仍然成立，也仍然是理解第十章的前提。

## 一、动机

前面几章的加法器和乘法器不只给 CPU 的协处理器用。
矩阵加速器里有 32 路乘累加，渲染加速器里有 14 个乘法器和 6 个加法器，
向量引擎的执行单元里也是同一批模块。

这一章讲两件事：同一个加法器换到乘累加环境里之后出的一个问题，
以及为什么这些模块要从矩阵加速器的目录里搬出来。

时间上它发生在[第三章](03-FP32加法器的三级流水实现.md)之前：
三级流水的加法器能上去，前提是这里先把反馈环改成能容纳多拍加法器。

## 二、为什么这一章的问题跟前面都不一样

### 前面几章没有反馈

前面每个单元的形状都是一条单向的流水线：

```
   输入 ---> [级1] ---> [级2] ---> [级3] ---> 输出

   第 k 笔和第 k+1 笔互不相干，可以一拍接一拍地喂
```

延迟长一点无非是结果晚出来，吞吐不受影响。

乘累加不是这个形状。它把加法器的输出接回了加法器自己的输入：

```
   积 ---> [ 加法器 ] ---> [ acc ]
                ^             |
                |             |
                +-------------+
                  反馈
```

### 反馈把"延迟"变成了"依赖距离"

一旦成环，第 k 项要读的 acc，是第 k-1 项写进去的。
延迟不再只是"结果晚出来"，而是"下一项要等多久才能开始"：

```
   没有反馈                        有反馈

   第 k 笔   |=====|                第 k 项   |=====| 写 acc
   第 k+1 笔  |=====|               第 k+1 项        |=====|
   第 k+2 笔   |=====|                              ^
                                        必须等 acc 写完才能开始读
   一拍一笔，满吞吐                 每隔若干拍才能喂一项
```

所以这一章要回答的问题不是"算得多快"，是"隔多久能喂下一项"。
这个间隔有个名字叫启动间隔（initiation interval），下面简称 Pace。

### 步骤由这个问题生出来

```
   一  定结构        一个乘法器、一个加法器、一个累加器
   二  定 Pace       算出隔多久能喂一项                <- 反馈带来的核心问题
   三  让 last 跟着走 因为有延迟，"最后一项"不能在输入端用 <- 流水带来的连带问题
```

## 三、每一步做了什么

### 3.1 结构

```
   a ---+
        | [ 乘法器 ] --- 积 ---+
   b ---+                      |
                               v
                          [ 加法器 ] --- 和 ---+
                               ^                |
                               |                v
                               +----------- [ acc ]
                                    读回上一次的累加值

   另有一条加载通路，可以把外部的部分和直接写进 acc
```

常规实现，没有技巧。

### 3.2 定 Pace

加法器是 3 级流水，所以不能每拍喂一个积：

```
   如果每拍喂一个（Pace = 1）

   拍号      0     1     2     3     4
   积 0    进入
   积 1          进入
   积 2                进入
   acc 更新              ^ 积 0 的和这时候才写进 acc

   积 1 在拍 1 就读了 acc，那时候积 0 的和还没写进去
   读到的是过期值
```

解决办法是降速喂入：每隔 Pace 拍喂一个积，
同一时刻累加环里只有一个加法在飞：

```
   Pace = 4

   拍号     0    1    2    3    4    5    6    7    8
   积 0   进入  --   --   --  写acc
   积 1                        进入  --   --   --  写acc
                               ^
                     这时候 acc 已经是积 0 的结果了
```

吞吐降到 1/Pace，但单累加器没有冒险。Pace 该取几，是第四节的内容。

还有一种做法是开若干个累加器轮流累加，保住满吞吐，最后再把它们加起来。
我们没做，因为实测这个加速器是访存受限的，算力不是瓶颈，
多开累加器只会增加面积和复杂度。

Pace 这个数存在 `rtl/fp32_lat.vh`，跟五个计算单元的流水延迟放在一起。
它是调用方要遵守的契约：喂快了模块不反压也不报错，所以这个数必须放在
调用方也能读到的地方。NPU 的调度器和各 TB 都从那里取值。

它在那里写成一个表达式：

```verilog
`define FP32_MAC_PACE (`FP32_ADD_LAT + 1)
```

这样写的理由是下一节的推导结论：这个间隔完全由加法器的级数决定。
挂在 `FP32_ADD_LAT` 上以后，加法器改级数时调度器和 TB 一起跟着变。

### 3.3 让 last 跟着数据走

"这是最后一个积"这个信息在输入端产生，但要在输出端用。
中间隔着乘法器的 2 拍和加法器的 3 拍：

```
   数据   积 ---> [乘法器 2 拍] ---> [加法器 3 拍] ---> 和
   控制   last -> [ 移 2 拍 ] ----> [ 移 3 拍 ] ----> 这时候才用

                  两条链的级数必须一样，否则错位
```

这种影子流水在整个仓里到处都是：数据打几拍，控制信号就跟着移几拍。
前提是没有反压；有反压就得配握手信号，纯移位不成立。

两条链的深度同样取自 `fp32_lat.vh` 的 `FP32_MUL_LAT` 和 `FP32_ADD_LAT`，
写成 `reg [`FP32_MUL_LAT-1:0] ml_pipe` 这样的位宽。链深跟对应计算单元的
流水级数是同一个数，只在一处定义。

## 四、遇到的问题

### 4.1 Pace = 3 算出来少一半

**第一现场。** 直觉答案是 Pace 等于加法器的级数 L，也就是 3。
按这个数实现，跑一个四项点积，四个数全是 `1.0`，期望 4.0：

```
MISMATCH dot=0: got=40000000 exp=40800000 ulp=4194304
==== fp32_mac_unit (降速单累加) vs 顺序点积 IEEE 金标准 ====
total=1  bad=1  maxulp=4194304
FAIL
```

**解读。** `40000000` 是 2.0，`40800000` 是 4.0。

结果正好是期望的一半。这个形状很有信息量：

```
   如果是加法器算错      四个 1.0 相加不会正好得到 2.0
   如果是溢出或 NaN      会得到 Inf 或者 7fc00000 之类
   如果是随机的时序问题   每次跑的结果应该不一样

   拿到的是整整齐齐的一半 => 四项里只有两项被累加进去了
   而且丢的方式是规律的（每两项丢一项）
```

所以要查的是节拍，不是数值通路。

**定位。** 写了一个逐拍打印的调试 TB，把"积就绪"、"加法完成"、
"acc 当前值"三个信号逐拍打出来。看到的是：

```
   拍号       ...    k     k+1   ...
   积就绪            ^
   加法完成          ^                <- 两个信号落在同一拍
   acc 的值        旧值   新值

   第 k 个积的加法在这一拍读 acc（组合读，读的是当前值 = 旧值）
   而 acc 要到这一拍的末沿才被第 k-1 个积更新
```

画成环路的形状：

```
   acc ---> [ 加法器 3 级 ] ---> [ acc 寄存 1 级 ] ---> acc
    ^                                                   |
    +---------------------------------------------------+

   一圈走过的级数 = 3 + 1 = 4，不是 3
```

**根因。** 环路里除了加法器的 3 级，还串着累加寄存器自己那一级。
环路延迟是 L+1。

**修法。** Pace 改成 4。四项点积得 4.0。

这个数现在写在模块头注释里，并且有一个 3000 条点积的 TB 断言它：
对顺序 IEEE 金标准逐位相同。常量的唯一真源在一个头文件里，
调度器和 TB 都引用它，不另写裸数字。

**方法。** 计算反馈环的启动间隔时，别只数运算单元的级数。
目的寄存器本身也在环里。

## 五、结果

这一章不产生独立的性能数字，它产生的是第三章那个三级流水加法器的落地条件。

验证上有一条判据值得单独说。TB 比的不是"数值接近"，
是跟"按顺序一个一个用 IEEE 加法累加"的结果逐位相同：

```
   浮点加法不满足结合律

   (a + b) + c   可能不等于   a + (b + c)

   所以"累加顺序"本身是结果的一部分
   这条判据锁定的是硬件的累加顺序跟金标准一致，不只是数值接近
```

3000 个点积，0 ULP。

延迟常量另有一组判据，在 `sim/tb_fp_lat.v`。它实测五个计算单元
`in_valid` 到 `out_valid` 的拍数，与 `fp32_lat.vh` 里的宏比对；对 MAC 另测两条：
末项到 `out_valid` 的合成延迟，以及首项到 `out_valid` 的距离等于
K-1 个喂入间隔加一次合成延迟。

喂入间隔本身从两头夹：

```
   按 Pace   拍喂入   ->  结果与金标准逐位相同
   按 Pace-1 拍喂入   ->  结果必须不同
```

只测上面那条的话，Pace 填成 100 同样能通过。下面那条给出的是"这个数不能再小"。
13 条判据全部通过。
