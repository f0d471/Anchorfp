# FP32 数据通路的 hold 时序修复

## 一、动机

### 上一章留下的余量

[第四章](04-FP32加乘单元的FTZ语义实现.md)为了修 Inf 的符号，在加法器级 2 加了一个寄存器。它进网表之后，
hold 余量从 50 皮秒降到 10 皮秒，只剩两成。这一章处理它。

### hold 为负意味着什么

hold 违例跟 setup 违例不是一类东西。

setup 违例说的是"这个频率跑不了"，把时钟降下来它就消失。
hold 的式子里根本没有周期（二、里写出来），降频对它完全无效 ——
一颗 hold 为负的片子在任何频率下都是坏的。

它的第二个性质更麻烦：不吵。

```
   综合    照常出 bitstream
   实现    照常跑完
   程序    照常启动，串口照常刷
   症状    输出是错的数，不是崩溃
```

这个项目在这上面吃过的亏记在 `_raw/Evolution/17`。
最贵的一次是 `result_writer` 写 BRAM 那条零逻辑级路径：**时序报告全项 MET，
板上系统性乱码**。真因是工具按"时钟共径长"扣掉了 209 皮秒的悲观量（CPR），
而 BRAM 的时钟走专用列网络，实际共径远短于工具的估计，真实余量是负的。
那一轮还得到一条更狠的结论：任何改变网表内容的 RTL 改动，
哪怕一行、哪怕运行时恒等无操作，都会重排布局、把那条路径重新暴露出来。

所以这里的因果关系是单向的：

```
   时序报告 MET  ->  片子是对的       不成立，本项目已经实证过反例
   hold 为负     ->  片子是错的       成立，而且降频救不回来
```

时序不是提交前要过的一道关。它是功能正确性本身，只不过这一类错误
不出现在仿真里，只出现在真实的片子上 —— 仿真器不知道走线有多长。
时序报告是这类故障唯一的提前信号，而且这个信号本身还不完全可靠。

### 这颗芯片的处境

我们这颗芯片填得很满，hold 余量长期在 10 到 30 皮秒之间。
作为对比，收敛良好的设计通常在 0.5 纳秒量级：

```
   收敛良好的设计   |=================================| 500 ps
   我们             |=|                                 10~30 ps
```

在这个量级上，任何进网表的改动都可能把余量推到负数，
包括不增删任何一个门的改动 —— 4.3 和 4.4 各有一次实测。
这就是为什么每条 FP 指令落地之后都要回头看一次 hold 余量。

## 二、为什么修 hold 只有那两种办法

### 两种检查，两条式子

时序分析有两个方向，对应两条式子。写出来就能看出它们的性质完全不同：

```
   setup 余量 = 周期 - 发射延迟 - 组合逻辑最长路径 - 建立时间 + 偏斜
                 ^^^^
                 周期在式子里

   hold  余量 = 发射延迟 + 组合逻辑最短路径 - 保持时间 - 偏斜
                （没有周期）
```

setup 检查的是"数据来得及吗"，跨一个周期：本拍发出，下一拍捕获。
周期越长越宽裕。

hold 检查的是"数据来得太早吗"，在同一个沿：这个沿发出的新数据，
不能在这个沿捕获上一笔数据之前就冲到目的端。

```
   同一个时钟沿
        |
        |--- 发射延迟 ---|--- 最短路径 ---|
        |                                 ^
        |                            新数据到达
        |
        |--- 保持时间 ---|
                         ^
                    目的端要求在这之前别动
```

### 由此推出修法只有两类

周期不在 hold 的式子里，所以降频对它完全无效。式子里能动的只剩两项：

```
   hold 余量 = 发射延迟 + 组合逻辑最短路径 - 保持时间 - 偏斜
                            ^^^^^^^^^^^^                ^^^^
                            往短路径上加延迟         调时钟相位
```

其余两项由器件工艺决定，改不了。

所以这一章能做的事只有：把最短路径变长，或者调相位。
后者会触发全局重新布局，代价大，先试前者。

### 步骤

```
   一  定位          找出最短的那条路径落在哪
   二  改形态        把零逻辑的裸传改成必须穿一级逻辑的形式
   三  证明没被优化掉 综合器可能把重建式化简回裸传
   四  证明数值等价   改法在功能上必须一字不差
```

第三步和第四步是这一章里比修法本身更麻烦的部分。

## 三、每一步做了什么

### 3.1 定位

CI 报告里最差的那条 hold 路径终点是：

```
u_npu_top/u_mac_engine/u_pe_array/PE_LANE[21].u_mac/u_add/s2_spec_sel_reg
```

这个信号正是[第四章](04-FP32加乘单元的FTZ语义实现.md)为了修 Inf 符号新加的那个。
改动直接落在了临界点上，而且临界点本身就是新加的那个寄存器。

它有 32 份副本（32 路 MAC）。副本越多，布局器把某一份放到坏位置的概率越大。

### 3.2 改形态：把裸传变成要穿一级逻辑

加法器级 1 到级 2 之间有几条信号是零逻辑裸传：

```
   裸传（危险）

   [ 级1 寄存器 ] ------------------------> [ 级2 寄存器 ]
                    一根线，没有任何逻辑
                    最短路径 = 线延迟，接近零


   重建（安全）

   [ 级1 寄存器 A ] --+
                      |--- [ 一级查找表 ] ---> [ 级2 寄存器 ]
   [ 级1 寄存器 B ] --+
                      最短路径 = 线延迟 + 一级逻辑，被强制拉高
```

做法是把要传的那个值在级 1 拆成两个更窄的信号存起来，
到级 2 再用一个异或把它算回来。

同样的手法在乘法器上也用了一次：特殊值原来是一个 32 位组合值寄存下来，
到输出级只过一级选择器。改成寄存 5 个一位标志
（NaN / Inf / Zero / 选择 / 符号），输出级用三级优先级选择重建。
省了大约 928 个触发器（每路 29 位乘 32 路），最短延迟自然增大。

### 3.3 注释里那句"勿改"

重建式在数学上可以化简。加法器那两行如果按代数约掉，
会得到一个更短的等价写法：把某个信号直接取反。

这个化简不能做，理由在网表层面：

```
   化简后的形式：寄存一个信号的取反

   [ 寄存器 ] --> (反相器) --> [ 寄存器 ]

   而 Xilinx 7 系列的触发器 D 端没有反相输入
   综合器碰到这种形式，很可能改成：

   [ 寄存器 ] --------------> [ 寄存器 ]   （寄存正相副本）
                                  |
                                  +--> 用的时候再取反

   于是这条路径又退回零逻辑裸传，修复静默失效
   网表变了，而代码一个字没改，没有任何东西会报警
```

写成两个不同信号的异或，综合器必须掏一个查找表出来实现它，
最短延迟保住了。这是一行专门对抗综合器优化的代码，
它在功能仿真里跟简写版一字不差，只有在真实网表上才有区别。

所以那句注释是必须的。

## 四、遇到的问题

### 4.1 怎么证明重建没有被优化掉

**第一现场。** 修完之后 CI 的数字变好了：

| | 修之前 | 修之后 |
|---|---:|---:|
| WHS（hold 余量）| 0.010 ns | 0.028 ns |
| 最差 hold 路径落点 | `PE_LANE[21].u_mac/u_add/s2_spec_sel_reg` | 渲染加速器的 CSR 到 SRL |
| CPU 时钟域最差 hold 路径 | 零逻辑裸传 | CARRY4 进位链（1 级逻辑）|

**解读。** 前两行只说明余量变好了，不足以证明修法生效——
重新布局本身就会让数字变动，下一轮可能又变回去。

第三行提供了关键证据：它检查路径的**形态**，数值大小只作为辅助信息：

```
   修之前   [reg] ----------------> [reg]      0 级逻辑
   修之后   [reg] --> CARRY4 -----> [reg]      1 级逻辑
```

修完之后 CPU 时钟域的最差 hold 路径仍然落在加法器里，
但它已经从零逻辑裸传变成了级 2 内部那个加法的进位链。

这正是重建手法想要的形态：每条级 1 到级 2 的路径都至少穿一级逻辑。
如果综合器把重建式化简掉了，那条路径应该还是 0 级。

**方法。** 验证一个针对网表的改动，要看网表层面的形态指标，
不能只看余量数值。余量会因为布局而波动，形态不会。

### 4.2 怎么证明重建在数值上还是对的

**第一现场。** 做了一次注入实验：把重建出来的那个信号取反，重跑回归。

```
==== fp32_add vs IEEE golden ====
total      = 250000
exact(0ULP)= 250000  (100%)
off 1 ULP  = 0
max ULP    = 0
ALL PASS (250000/250000 逐位相同)
```

故意注错，25 万条向量全绿，一条都没红。

**解读。** 这个输出的含义是这条回归对这个信号的鉴别力为零。

原因是它只影响"两个异号的数精确相消到零"时那个零的符号
（[第三章](03-FP32加法器的三级流水实现.md) 3.3）。
要命中那种输入，需要两个随机的 32 位数除符号位外完全相同，
25 万条随机值碰不到。

**修法。** 真正能覆盖到它的是三条定向用例：

```
    1.0 - 1.0     期望 +0
   -0.0 - (+0.0)  期望 -0
   -0.0 - (-0.0)  期望 +0
```

板上这三条全对，就说明重建式在真实网表上等价。
这是整条线上鉴别力最强的一条判据，而它只有三行。

**方法。** 注错见红是判据有效性的直接检验。
一条判据如果没有被注错验证过，"它覆盖了什么"只是推测。

### 4.3 删逻辑不等于给余量

**第一现场。** [第四章](04-FP32加乘单元的FTZ语义实现.md)结尾删掉了那个左移模块，
省了 7,363 个 LUT。当时的预期是逻辑少了、布局松了，余量应该回来一些。
CI 给出的是相反的结果：

| | 删之前 | 删之后 |
|---|---:|---:|
| Slice LUTs | 74,021 | 66,658（−9.9%）|
| WNS（setup 余量）| 0.663 | 0.161 |
| WHS（hold 余量）| 0.028 | 0.017 |
| 最差 hold 落点 | 渲染加速器的 CSR 到 SRL | 回到 `PE_LANE[26].u_mac/u_mul/p_reg[5]` |

**解读。** LUT 少了将近一万，两个余量都掉了，
而且临界点回到了被删逻辑的那个模块。

```
   期望的因果                    实际发生的

   删逻辑 -> 更空 -> 余量回来     删逻辑 -> 网表大改 -> 重新布局
                                                        |
                                          余量重新分配，方向不确定
                                                        |
                                    被删逻辑周围变化最大，
                                    反而更容易成为新的临界点
```

### 4.4 这个抖动跟改了什么没关系

**第一现场。** 把四轮 CI 的 hold 临界点排在一起看：

| 这个工作点改了什么 | 最差 hold 路径落点 | 余量 |
|---|---|---:|
| FTZ 语义 | MAC 阵列 `u_add` | 0.010 |
| 窄信号重建 | 渲染加速器 CSR 到 SRL | 0.028 |
| 删死码 | 回到 MAC 阵列 `u_mul` | 0.017 |
| 再下一轮 | 渲染加速器序列器内部 | 0.011 |

**解读。** 临界点在两个模块之间来回跳了三次：

```
   轮次      1        2        3        4
   落点     MAC ---> 渲染 ---> MAC ---> 渲染
   余量     10 ps    28 ps    17 ps    11 ps

   最后那一轮一个字都没碰这两个模块
```

所以这不是某个模块的 hold 缺陷，是这个规模的设计在布局器手里的固有抖动。

**后果。** 我们曾经给新原语定过一条准入门槛：
hold 余量必须先回到 35 皮秒以上才允许再加单元。
这条门槛无法满足，四轮实测最高 28 皮秒，而且每次都被下一次布局洗掉。

门槛后来改成两条：全项 MET，并且最差路径不落在零逻辑裸传上。
后一条才是窄信号重建那个工作点真正起作用的地方。

### 4.5 一条被推翻的诊断

**第一现场。** 删死码那一轮之后，最差 hold 路径落在乘法器上。
当时的判断是"级深不均衡"：级 0 塞了一个 24×24 乘法器很深，
级 1 只有归一化和舍入很浅，应该重新切一下级。

查实际路径，报告给出的是：

```
源    PE_LANE[26].u_mac/u_mul/product_r_reg[28]/C
终    PE_LANE[26].u_mac/u_mul/p_reg[5]/D
逻辑  2 级（LUT3 归一化选择 + CARRY4 舍入进位）
数据  0.388 ns
偏斜  0.266 ns
```

**解读。** 最后两行是关键：

```
   这条路径的余量构成

   数据延迟   |==========================|  0.388 ns
   偏斜       |=================|           0.266 ns  <- 被这个吃掉大半
                                |=========|  剩下的才是余量
```

真正消耗余量的是偏斜，目的端的时钟比源端晚到 0.22 ns。
那是 32 份副本加上满布局的产物，跟逻辑写法无关。

而且 `逻辑 2 级` 已经是这个功能的最小深度，本身没有任何不规范。

**为什么"重新切级"这个方案不成立。** 因为它作用在错误的轴上：

```
   重排流水级深度   改变的是路径的平均长度和最长长度  -> 影响 setup
   hold 看的是      最短路径                        -> 不受影响

   把级 0 的活挪到级 1，低位那条
   product_r[k] -> 选择器 -> 加法器 -> p[j]
   还是 2 级，一点没变
```

**结论。** 重排级深度不解决 hold。可用的手段只有第二节推出来的那两条：
插显式延迟，或者调 PLL 相位。两条都会触发全局重新布局，
而 4.3 刚证明了大改网表可能更差。所以这一条记在账上，没动。

## 五、结果

hold 余量从 0.010 ns 回到 0.028 ns，CPU 时钟域的最差路径形态
从零逻辑裸传变成 CARRY4 进位链。数值等价由三条定向用例覆盖。

准入门槛从"余量 ≥ 35 ps"改成"全项 MET 且最差路径不落在零逻辑裸传上"。

---

CI 数据来自 Vivado 2019.2 的 `timing_summary.rpt` 和 `utilization.rpt`。
有一条测量上的注意事项：这份报告每个时钟组只打印一条最差路径，
所以"MAC 阵列的余量大于 28 皮秒"是从"它没出现在榜首"反推的，不是直接测量。
要精确对账得单独跑 `report_timing -delay_type min -to [get_cells */u_mac/u_add/*]`。
