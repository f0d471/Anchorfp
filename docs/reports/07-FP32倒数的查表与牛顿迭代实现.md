# FP32 倒数的查表与牛顿迭代实现

## 一、动机

### 剩下的最贵一项

转换做完之后，没有硬件的算术原语只剩除法，软件版 261.64 拍，
是所有原语里最贵的。

按前面五章的路子，下一步应该是把 `__divsf3` 也换掉。
一开始我们就是这么打算的，代码注释里还写着"典型 1 到 2 ULP"。

### 为什么最后没有换掉除号

IEEE 754 把运算分成两类：

```
   必须正确舍入                        不要求
   +  -  x  /  sqrt  fma               exp  log  sin  cos  pow
   整数与浮点的转换                     标准只在推荐章节里给建议
   比较

   "正确舍入"的意思是：
   结果必须等于用无限精度算完再舍入一次，一位不差
```

除法在第一类里。用近似倒数替换它，等于把 C 的除号从 0 ULP 变成 1e-3 量级。
llama2 和 lenet 的输出会整体改变。

业界处理同一件事的方式是：近似倒数是一条独立的显式指令。

```
   x86        RCPSS
   ARM        VRECPE
   RISC-V     vfrec7.v

   编译器默认绝不拿它们替换 /
   只有开了 -ffast-math 或 -freciprocal-math 才允许
```

所以这一章的目标改成两条：提供一条显式的近似倒数指令，谁用谁负责容差；
不替换 `__divsf3`，C 的 `/` 保持 libgcc 的 0 ULP。

顺带把我们其他几处偏差对照了一遍：

```
                       我们       x86        ARM       RISC-V
   FTZ                 开         可开       可开        —        对标
   超越函数精度        11.6 位      12 位      8 位       7 位      对标
   用近似替换除号        不做        不做       不做       不做      对标
```

### 延迟预算

这条指令比前面几条都深：查表要一拍存储器读延迟，
牛顿迭代要两个定点乘法，每个占一级。最后落在 5 级。

5 拍在阻塞式接口里仍然是很贵的单价，但它换来的是从 261.64 拍降下来，
仍然划算。这也是这条线上延迟最长的一个单元。

## 二、为什么是这五步

### 除法为什么在硬件上贵

加减乘都可以一遍并行算完：所有位同时参与，结果一次出来。
除法不行，商的每一位都依赖前一位算出的余数：

```
   长除法的形状

   商的第 1 位  <- 由被除数决定
   商的第 2 位  <- 由第 1 位算完的余数决定
   商的第 3 位  <- 由第 2 位算完的余数决定
   ...

   24 位商 = 24 步串行，无法并行
```

这是除法贵的根本原因，跟实现技巧无关。

### 第一次绕开：把除法换成乘法

```
   a / b   =   a x (1/b)
                    ^
              只剩一个操作数
```

变成两件事：求 `1/b`，然后做一次乘法。乘法已经有了。

但 `1/b` 本身还是一个除法。这一步没有消灭除法，只是把它化成了
一个更窄的问题：被除数固定是 1，只剩一个操作数。

### 第二次绕开：不去"算"倒数，改成"猜了再验"

把问题反过来问一次。

"算出 `1/m`"要走长除法。但我们其实不需要算出它，只需要**找到**它。
找就要能判断找对没有，于是先问：给一个数 `r`，怎么判断它是不是 `1/m`？

```
   判断 r 是不是 1/m ：算 m x r，看等不等于 1

   一次乘法。没有除法。
```

这就是整件事的转折点：**求倒数要除法，检验倒数只要乘法。**
既然检验便宜，就可以把"算"换成"猜一个，验一下，不对就改"。

剩下两个问题：从哪儿开始猜，以及按什么规则改。

### 改的规则：牛顿法

先把"`m x r` 等于 1"写成求根的形式，也就是找一个 `r` 让某个函数 `f(r)` 等于零。

牛顿法用一句话就能说完：**在当前猜测那一点作曲线的切线，
切线跟横轴的交点，就是下一个猜测。**

```
   f(r)
    |     \
    |      \  曲线
    |       \
    |    \   \
    |     \   \      在 r0 这一点作切线
    |      \   \
   -+-------\---o----------------> r
    |        \  r0
    |         o
    |         r1 = 切线与横轴的交点
    |
   曲线弯，切线直。切线的零点比 r0 更靠近曲线的零点。
```

写成公式就是

```
   r(n+1) = r(n) - f(r(n)) / f'(r(n))
```

到这里都还是通用的牛顿法。**接下来这一步才是这个模块的关键：
"`m x r = 1`"可以写成不止一个 `f`，而选哪个 `f` 决定了迭代式里有没有除法。**

```
   写法一   f(r) = m*r - 1        f'(r) = m

            r(n+1) = r(n) - (m*r(n) - 1) / m
                                          ^
                              要除以 m。绕了一圈又回到除法，白忙

   写法二   f(r) = 1/r - m        f'(r) = -1/r^2

            r(n+1) = r(n) - (1/r(n) - m) / (-1/r(n)^2)
                   = r(n) + r(n)^2 * (1/r(n) - m)
                   = r(n) + r(n) - m*r(n)^2
                   = r(n) * (2 - m*r(n))
                            ^^^^^^^^^^^^
                     只有乘法和减法。式子里再也没有除号
```

两个写法描述的是同一个方程、同一个根，迭代式却一个能用一个不能用。
`f(r) = 1/r - m` 里那个 `1/r`，在求导之后跟分母上的 `1/r^2` 约掉了，
这是它能用的原因。

所以迭代式是

```
   r1 = r0 x (2 - m x r0)
```

它不是凑出来的，是选定 `f(r) = 1/r - m` 之后由牛顿法直接推出来的。

### 一轮就够：误差每轮平方

定义相对误差

```
   e = 1 - m*r          r 恰好等于 1/m 时 e = 0
```

把迭代式代进去：

```
   m*r1 = m * r0 * (2 - m*r0)

   令 m*r0 = 1 - e0：

   m*r1 = (1 - e0) * (2 - (1 - e0))
        = (1 - e0) * (1 + e0)
        = 1 - e0^2

   => e1 = e0^2
```

一行代数，同时给出两个结论。

**结论一：误差每轮平方。** 这就是"二次收敛"的含义。

```
   e0 = 2^-11
        |    平方
        v
   e1 = 2^-22

   FP32 尾数 23 位，2^-22 已经落在最低两位上，一轮就够
```

**结论二：`e1 = e0^2` 恒大于等于零，所以 `m*r1` 恒小于等于 1，
也就是 `r1` 恒小于等于 `1/m`。** 迭代永远从下面逼近真值，取不到等号
（除非 `e0` 本来就是零）。这条性质后面会逼出第四步，见 3.4。

### 从哪儿开始猜：查表

误差预算倒着推：

```
   想要   e1 <= 2^-22
   而     e1 = e0^2
   所以   e0 <= 2^-11
```

初值的相对误差必须优于 `2^-11`。靠公式凑一个这么准的初值不现实，
办法是**查表**：把输入区间切成若干段，每段的答案预先算好存起来。
一张 1024 项的表正好能给到 `2^-11`，这笔账在 3.2 节算。

### 指数不用逼近

浮点数的指数部分可以直接算，不参与逼近：

```
   a = 正负 2^(e-127) x m,     m 属于 [1, 2)

   1/a = 正负 2^(126-e) x (2/m)
              ^^^^^^^^^^^   ^^^^^
              一个减法        只有这部分需要逼近
```

所以第一步是把指数剥掉，只对 `[1, 2)` 区间里的尾数求倒数。
这也让表只需要覆盖一个固定区间，1024 项就够。

### 五步的由来

```
   一  拆掉指数      1/a 化成"阶码取反"加"尾数求倒数"    <- 指数可以直接算
   二  查表          给 1/m 一个 2^-11 的初值            <- 逼近法要初值
   三  牛顿迭代      一轮把误差平方到 2^-22               <- 逼近法要迭代
   四  特判 2 的幂   迭代单调从下逼近，到不了精确值       <- e1 = e0^2 >= 0
   五  规格化组装    定点结果转回 FP32                   <- 内部是定点，接口是浮点
```

切流水不单算一步，它贯穿这五步，见 3.6。

## 三、每一步做了什么

### 3.1 拆掉指数

```
   输入 a   +-+--------+-----------------------+
            |s|   e    |          f            |
            +-+--------+-----------------------+
             |    |                 |
             |    |                 +--> m = 1.f，送去求倒数
             |    +--> 253 - e，一个减法就是结果的阶码
             +--> 符号原样带过去
```

那个 253 是这么来的：

```
   a   = (-1)^s x 2^(e-127) x m,        m 属于 [1, 2)

   1/a = (-1)^s x 2^(127-e) x (1/m)

   但 1/m 落在 (0.5, 1]，不在 [1, 2)，不是合法的规格化尾数。
   把 2 挪一下：

   1/a = (-1)^s x 2^(126-e) x (2/m),    2/m 属于 [1, 2)   <- 这才是规格化形式

   结果要存的偏移阶码 = (126 - e) + 127 = 253 - e
```

顺带说明了一件事：**逼近算出来的是 `1/m`，而结果的尾数是 `2/m`。**
两者只差一位移位，这一位在第五步兑现。

### 3.2 查表

**表存什么。** 把 `[1, 2)` 按尾数的高 10 位切成 1024 段，每段存一个倒数初值：

```
   m 的区间      1.0                                     2.0
                 |--|--|--|--| ....................... |--|
                  0  1  2  3                          1023
                  每段宽度 2^-10

   第 i 段覆盖   m 属于 [1 + i/1024,  1 + (i+1)/1024)
```

**表怎么来的。** 不是硬件算的，是 PC 上一个几十行的 C 程序算好、打印成文本，
综合时由 `$readmemh` 读进 BRAM 的初值。也就是说**这张表是 bitstream 的一部分，
上电就在那里**，运行时只有读，没有算。

```
   gen_recip_lut.c          编译运行         recip_lut.mem       综合时 $readmemh
   (double 精度算 1024 个    ----------->    (1024 行十六进制)   -------------->  BRAM 初值
    值，避免表本身带
    float 的舍入误差)
```

生成规则一行就写完：

```
   m_mid = 1 + (i + 0.5) / 1024          区间中点
   r0    = round( 1/m_mid * 2^17 )       转成定点存进去

   i=0     m_mid=1.000488281   1/m_mid=0.999511957   ->  0x1ffc0
   i=512   m_mid=1.500488281   1/m_mid=0.666449723   ->  0x15539
   i=1023  m_mid=1.999511719   1/m_mid=0.500122100   ->  0x10010
```

**地址怎么来的。** 就是尾数的高 10 位，一段裸切片，不经过任何逻辑：

```
   frac    22                     13 12              0
          +------------------------+------------------+
          |     表地址（高 10 位）  |     低 13 位      |
          +------------------------+------------------+
                     |
                     +--> 直接接到 BRAM 的地址口
```

**这里用了一个特定手段：表里存区间中点的倒数，不存左端点的。**

一段的宽度是 `2^-10`。表项对准哪里，决定了真实的 `m` 最远能离它多远：

```
   存左端点                             存中点

   m_left           m_right             m_left      m_mid     m_right
     |-----------------|                  |-----------|-----------|
     ^                                                ^
     表项对准这里                                 表项对准这里

     |<-- 最远差一整段 2^-10 -->|          |<-半段->|<-半段->|
                                            最远差 2^-11
```

写成算式，因为表项 `r0` 就是 `1/m0`（`m0` 是那一段的代表点）：

```
   e0 = 1 - m*r0 = 1 - m/m0 = (m0 - m) / m0

   m0 取左端点   |m0 - m| < 2^-10,  m0 >= 1   =>   |e0| < 2^-10
   m0 取中点     |m0 - m| <= 2^-11            =>   |e0| <= 2^-11
```

对 1024 段逐段扫一遍，两个上界都精确取到。再套 `e1 = e0^2`：

```
                初值误差 e0     牛顿一轮后 e1      换算成 ULP
   左端点        2^-10          2^-20             8 到 16
   中点          2^-11          2^-22             2 到 4      <- 实测最大 4
```

（ULP 换算：结果尾数落在 `[1, 2)`，1 个 ULP 的相对大小在 `2^-24` 到 `2^-23` 之间，
所以同一个相对误差换算成 ULP 会有一倍的区间。）

改一次表白赚一位初值精度，牛顿把它放大成两位结果精度。
代价只是重新跑一次生成器。作为对比，多加一轮牛顿要多两个乘法器，
其中一个是 42 位的。

**为什么是 18 位（Q0.17）。** `r0` 落在 `(0.5, 1]`，18 位无符号定点刚好装下，
`1.0` 对应 `0x20000`。量化误差 `2^-18` 远小于区间误差 `2^-11`，不吃精度预算。
BRAM 的字宽是 32 位，高 14 位空着不用。

**一条附带的教训。** 那张表原来没有生成器，仓里只有一个 `.mem` 文件，
存的是左端点这件事是从数值逐条反推出来的。补了生成器之后，
表的口径才有唯一真源。凡是进 RTL 的表，都要有可复现的生成器。

### 3.3 牛顿迭代在定点上怎么算

模块内部全是定点。记号 `Qa.b` 表示整数部分 `a` 位、小数部分 `b` 位，
也就是"小数点在第 `b` 位上"。比如 Q1.23 里 `0x800000` 表示 1.0。

一轮迭代拆成两个乘法，各占一级流水：

```
   m     24 位   小数点在第 23 位   值属于 [1, 2)
   r0    18 位   小数点在第 17 位   值属于 (0.5, 1]

   t  = m x r0        24 x 18 -> 42 位，小数点落到第 40 位
                      值 = 1 - e0，恒在 1 附近

   d  = 2 - t         42 位，小数点仍在第 40 位
                      这里的常数 2 在这个格式下就是 2 x 2^40 = 0x200_0000_0000
                      一个常数减，几乎免费

   r1 = r0 x d        18 x 42 -> 60 位，小数点落到第 57 位
                      值 = 1/m 的估计，属于 (0.5, 1]
```

小数点位置是相加的：`23 + 17 = 40`，`17 + 40 = 57`。这就是位宽的来历，
没有别的选择余地。

收敛的形状：

```
   误差
    |
    | 2^-11   o
    |          \
    |           \   平方
    |            \
    | 2^-22       o
    |
    +------------------> 迭代轮次
         0        1
```

### 3.4 特判 2 的幂

二、里已经证过：`e1 = e0^2` 恒大于等于零，所以迭代永远从下面逼近，取不到等号。
画出来是这样：

```
   真值 1/m  ------------------------------
                                     o  r1（永远差一点）
                           o  r0
   ----------------------------------------> 迭代
```

对绝大多数输入这没关系，差的那点在容差里。但对 2 的整数次幂不行：

```
   1/2.0    真值 0.25       算出来 0.24999998
   1/4.0    真值 0.125      算出来 0.12499999

   这些数是精确可表示的，用户对它们的期望是必须精确
```

判据很简单：输入是 2 的幂，等价于尾数的小数部分全为零，也就是 `m` 恰好等于 1.0。
一个 23 位的或非门。

这时候 `1/m = 1`，结果尾数 `2/m = 2.0`，正好是"尾数进位到 2.0"这一种情况，
而那条通路第五步本来就有（舍入进位也会走到它）。所以特判不需要另建一条支路，
把进位信号强行置 1 就行。代价只有那个或非门。

x86 的 `RCPSS` 之类估计指令同样保证这一类精确，这是这类指令的惯例。

### 3.5 规格化与组装

现在手上是一个 60 位定点数 `r1`，值是 `1/m`；要交出去的是一个 32 位 FP32，
尾数部分是 `2/m`。差的那一倍，就是把小数点右移一位看。

```
   r1   60 位，小数点在第 57 位，值属于 (0.5, 1]

   bit  59 58 57 56 55 ................ 33 32 31 ................ 0
         0  0  ?  1  <----- 23 位 ----->  G  <------ 32 位 ------->
               ^  ^                       ^         ^
               |  |                       |         +-- 全部或起来 = sticky
               |  |                       +------------ guard
               |  +--- 结果尾数的隐藏位（把 r1 当作 2/m 来读，小数点右移一位）
               +------ 只有 r1 恰好等于 1 时才是 1
```

于是取位窗直接读：隐藏位在 bit 56，23 位小数在 bit 55 到 33，
guard 在 bit 32，再往下 32 位全部或起来当 sticky。舍入规则是 RNE，
跟前面几章的乘法器、加法器完全一样，属于常规做法。

代码取的是 `[57:33]` 共 25 位而不是 24 位，多的那一位是给进位留的位置：

```
   mant_s = {1'b0, 25 位} + round_up          26 位

            mant_s[22:0]   结果的 23 位小数
            mant_s[23]     隐藏位
            mant_s[24]     进位到了 2.0  ->  小数清零，阶码加一
```

3.4 节那条特判走的就是最后这一行。

阶码在 3.1 已经算好，这里只做封顶：

```
   exp = (253 - e) + (进位 ? 1 : 0)

   exp <= 0     下溢，按 FTZ 输出正负零
   exp >= 255   上溢，输出正负无穷
```

特殊值按固定优先级覆盖常规通路：

```
   NaN          原值透传
   正负 Inf     ->  正负 0
   正负 0       ->  正负 Inf
   denormal     按 FTZ 当作零处理，同样给出正负 Inf
   其余         走上面的常规通路
```

### 3.6 切流水

```
   级 1   拆包、分类；同一拍表读在途
   级 2   收表项
   级 3   第一个乘法    m x r0
   级 4   第二个乘法    r0 x (2 - t)
   级 5   规格化、舍入、组装
```

两个定点乘法各占一级。

表存在同步读的存储器里，地址在时钟沿被锁存，数据要下一拍才出来：

```
   时钟沿      沿1        沿2        沿3
              |          |          |
   地址    ---+ 有效 +----|----------|
              |          |
   数据    ---|----------+ 有效 +----|
                         ^
                    要等一整拍
```

这一拍等待不需要单独一级去消化。表地址是输入尾数的一段裸切片，
不经过任何逻辑，直接接到存储器的地址口上就行；存储器自己会在沿上锁存它。
于是级 1 在寄存尾数和旗标的同时，表读已经在途，级 2 直接收表。

一开始不是这么写的，代价是白花了一级，见 4.4。

## 四、遇到的问题

### 4.1 18 条定向用例挑的全是自己能过的点

**第一现场。** 补牛顿迭代之前的版本只有查表，没有迭代。
当时的 `tb_fp32_recip` 跑出来是这样：

```
-- special (bit-exact) --
  PASS: 1/+0 -> +Inf
  PASS: 1/-0 -> -Inf
  ...
-- powers of two (bit-exact) --
  PASS: 1/1.0 = 1.0
  PASS: 1/2.0 = 0.5
  PASS: 1/4.0 = 0.25
  ...（18 条定向全 PASS）
  random golden: loaded=20021 compared=20021 over-tol=19770 max_ulp=16011
  FAIL: 19770/20021 超容差
```

**解读。** 两段的反差本身就是线索。

```
   定向段    18 / 18      全过
   随机段    251 / 20021  过，19770 条超容差，98.7% 不过
```

一个实现如果正确，两段应该同时过；如果错了，两段应该同时露馅。
只有定向过、随机不过，说明定向段选的点有系统性。

`max_ulp=16011` 这个数还给出了错误的量级。当时的表存的是左端点，
只查表不迭代的相对误差就是 `2^-10`；按 3.2 那张换算表，
`2^-10` 对应 8192 到 16384 个 ULP，实测的 16011 正落在这个区间的上端。
差的不是精度微调，是整整一轮迭代。

**定位。** 看那 18 条用的是什么数：`1.0`、`2.0`、`3.0`、`4.0`、`0.5`、
最小规格化数。这些数的尾数低 13 位全是 0。

而表的地址取的是尾数的高 10 位：

```
   尾数     22                     13 12              0
           +------------------------+------------------+
           |    表地址（高 10 位）   |     低 13 位      |
           +------------------------+------------------+
                                       ^
                        这 13 位全为 0 => 这个数正好落在表的格点上
                        => 查表结果就是精确值，迭代做不做都一样

   定向用的 1.0 / 2.0 / 4.0 / 0.5，低 13 位全是 0
```

定向段的鉴别力是零。

**修法。** 补三条落在格点之间的用例：`1/1.7`、`1/π`、`1/√2`。
补完之后定向段能独立暴露"缺牛顿迭代"。

**方法。** 定向用例里必须至少有一个"如果实现偷懒就会错"的点，
而且写用例的时候就要想清楚它防的是哪一类偷懒。
挑好记的整数值最容易踩这个坑，因为好记的数往往也是特殊的数。

### 4.2 修了两个真 bug，一个数都没变

**第一现场。** 同一轮还查出两处结构错误：

```
   错误一   表是同步读，而第一版在下一拍就去收数据
            早采了一拍，收到的是上一笔的表项

   错误二   valid 链是 5 级而数据链是 4 级
            错位一拍
```

两处都改对了。改完重跑随机对拍：

```
  random golden: loaded=20021 compared=20021 over-tol=19770 max_ulp=16011
  FAIL: 19770/20021 超容差
```

跟改之前逐字相同，一个数都没变。

**解读。** 改对了两处真错误而指标零变化，
说明这两处错误在当前激励下没有任何可观测效应。

**定位。** 看 testbench 的激励形态：

```
   TB 的激励（输入一直保持不变）

   a      ==== 同一个值一直挂着 ====
   addr   ==== 每拍重载同一个地址 ====
   数据   ==== 每拍读出同一个表项 ====

   早采一拍   -> 读到的"上一笔表项"跟这一笔是同一个值
   错位一拍   -> 读到的还是同一笔数据

   流水自己就对上了
```

**结论。** 这两条属于结构上错、当前激励下无表现。
真正的表现要等背靠背或者单拍激励，
跟[第一章](01-标量浮点协处理器接口设计.md) 4.2 那个背靠背死锁
是同一件事：保持型激励掩盖了时序相关的缺陷。

### 4.3 表放错目录，两个月里每颗 bitstream 都是空表

**第一现场。** 综合日志里有一行：

```
CRITICAL WARNING: [Synth 8-4445] cannot open file recip_lut.mem
```

板上 FRECIP 返回垃圾，持续两个月。

**解读。** 这条 warning 的级别是 CRITICAL，但它不让综合失败：

```
   综合   出 warning，继续
   实现   照常跑
   时序   照常报 MET
   CI     照常出 bitstream，判通过

   在几千行日志里它只占一行
```

读表文件失败的后果不是"读到错误的表项"，
是数组保持初值，综合器把它优化成常量：

```
   期望的电路                      实际综合出来的电路

   地址 --> [ ROM 1024x32 ] --> 数据      地址 --> (常量) --> 数据
                                                    ^
                                        ROM 既没有初值也没有写口
                                        整条读通路被优化掉了
```

所以板上不是"表里的数不对"，是根本没有表。

**定位。** 裸文件名的解析规则是：按发起读取的那个 `.v` 文件所在的目录去找。

```
   五张表的位置

   rtl/    exp 表     跟 bram 模块同目录     读得到
   rtl/    sin 表     同上                   读得到
   rtl/    rsqrt 表   同上                   读得到
   rtl/     recip 表   跟它的消费者同目录      读不到
                              ^
                  放在了"使用结果的模块"旁边；正确位置应靠近读取表文件的模块
```

**旁证。** 这件事同时解释了两个一直没有解释的数：

```
   预算 vs 实测

   补两个定点乘法     预算 +1500 LUT    实测 +233 LUT   差得离谱
   加一张 1024x32 表  预算 +1 块 BRAM   实测 +0 块      一块没涨
```

两条都指向"这部分电路根本没被综合出来"。
当时两条数都摆在报告里，没有人把它们跟那条 warning 联起来。

**修法。** 把表文件挪回读它的那个模块所在的目录，
并把位置约束写死在那个模块的头注释里。

顺带改掉了造成事故的那句注释。原文写的是 `(sim only)`，
这四个字让人以为表文件只在仿真里有用、放哪儿都行。

**为什么判据没覆盖到。** 判据在，而且写得很对。
板上测试程序里一直有六条 frecip 判据，包括 `1/2.0` 和 `1/4.0` 的逐位相等、
三条非格点值的 4 ULP 容差。

问题是这六条没有进上板回归清单，两个月里没有被执行过。
判据存在跟判据被执行是两件事。

### 4.4 表地址被寄存了两次，白花一级流水

**第一现场。** 没有现场。没有仿真报错，没有板上异常，六拍的结果一直是对的。
这一条是整理这个系列时逐行读源码读出来的：

```verilog
   s1_addr <= s0_frac[22:13];        // 本模块寄存一次

   bram_lut_1024x32 ... .addr(s1_addr)
        always @(posedge clk) if (re) dout <= mem[addr];   // 存储器内部又锁存一次
```

**解读。** 同步读存储器自己会在时钟沿锁存地址，这是它"同步读"的含义。
在它外面再寄存一次地址，等于让地址走了两级触发器，
而数据只需要一级读延迟。多出来的那一拍必须有人消化，
于是就有了一个纯搬旗标、不做任何计算的级 2。

代价是延迟表上多一拍。对阻塞式协处理器来说，延迟就是单价。

**定位。** 判断依据是"这一级做了什么"。级 2 的时序块里没有算术，
只是把上一级的旗标原样搬到下一级。一个不改变任何值的流水级，
它存在的唯一理由只能是等某样东西 —— 这里等的是表读。
而表读的等待，存储器自己那一级已经提供了。

**根因和修法。** 表地址是 `frac[22:13]`，输入端口的一段裸切片，零逻辑。
把它直接接到存储器的地址口，级 1 在寄存尾数和旗标的同一拍，
表读已经在途，级 2 就能直接收表：

```
   改前   级1 存地址 -> 级2 等表 -> 级3 收表 -> 乘 -> 乘 -> 组装      6 拍
   改后   级1 存尾数(表读在途) -> 级2 收表 -> 乘 -> 乘 -> 组装        5 拍
```

组合深度一级都没变深，因为搬走的是一个寄存器，不是一段逻辑。

`rsqrt_func` 有一模一样的问题，同一处修法，也是 6 拍收到 5 拍。

**原来的判据为什么没覆盖到它。** 因为它不是错误。所有判据问的都是
"结果对不对"和"延迟是不是等于声明值"，而这两条当时都成立 ——
延迟声明的就是 6，实测也是 6。**多花一拍不会让任何判据变红。**

这一类问题只能靠读代码发现，问的是另一个问题：这一级存在的理由是什么。

改完之后要证明的是数值逐位不变，判据是把新旧两个版本并排例化、
喂同一批输入、按出队顺序逐位比较。20 万条随机输入加 8 个定向边界
（1.0、2.0、正负 0、Inf、NaN、denormal、最大规格数），失配 0。

## 五、结果

补完迭代、修完三个问题之后：

```
tb_fp32_recip: 21 PASS, 0 FAIL  (TOL=4 ULP)
  random golden: loaded=20021 compared=20021 over-tol=0 max_ulp=4
  worst case: a=e800c131 got=96fe7fde exp=96fe7fe2
```

正负零、正负无穷、NaN、FTZ、2 的幂全部逐位精确；三条非格点用例 0 ULP。
从 19,770 条不符、16,011 ULP 走到这里。

实测最大 4 ULP 跟 3.2 那笔账对得上：中点表给 `e0 = 2^-11`，
牛顿一轮到 `e1 = 2^-22`，换算成 ULP 是 2 到 4。

板上跟正确舍入的 `1.0f/x` 对比是 **29.76 倍**，单价 8.99 拍。
引用这个数必须带一句：两者语义不等价，
一个是正确舍入，一个是最大 4 ULP 的近似。

这个数替换了收一拍之前的旧值（9.99 拍 / 26.9 倍）。
**两次的差值正好是一拍**，收一拍那件事在板上是定量兑现的，不是"看起来没变慢"：

```
   收之前   9.99 拍   26.90 倍
   收之后   8.99 拍   29.76 倍
```

这也是 4.4 节那次修改唯一的**板上**证据。`rsqrt_func` 同批收的那一拍就没有这种证据——
`fpmark` 不测 rsqrt，板上只有 `vse_probe` 的自洽判据说明它算得对，
没有任何一处量过它的拍数。**同一批改动，两条的证据强度不一样，别混着引用。**

### 除号确实没被换掉的证据

这条规矩在板上得到了直接验证：

```
   __divsf3        261.64 拍     libgcc 的软件除法
   1.0f / x        263.62 拍     = 261.64 + 2 拍取常数

   倒数单元就在同一颗 bitstream 里，CI 也把它的资源算进去了
   而除号一拍都没变快
```
