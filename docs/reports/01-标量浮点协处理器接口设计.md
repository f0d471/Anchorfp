# 标量浮点协处理器接口设计

这是 FP 系列的第一章，讲骨架：为什么要做浮点硬件、为什么选协处理器这条路、
这个选择带来了什么约束，以及一条自定义指令从 C 源码到拿到结果，
中间哪些环节必须打通。后面每一章讲一条具体指令怎么做出来。

## 一、动机

### SoC和它的问题

我们的SoC跑在 Artix-7 xc7a200t 上，50 MHz。CPU 是龙芯 LA32R 指令集的一个精简实现，
片上还挂着一个矩阵加速器、一个渲染加速器和一路 DVI 输出。

跑在上面的负载有三个：llama2 推理、lenet 推理、一个三维高斯溅射渲染器。
三个都大量做浮点运算。

这颗 CPU 没有浮点单元。LA32R 的这个配置是软浮点，C 里写 `a * b`，
编译器发不出浮点乘法指令，只能发一条 `bl __mulsf3`，跳进 libgcc，
用整数指令把浮点乘法模拟一遍。

用紧循环探针量过，一个 FP32 乘法 131 个周期。反汇编那个函数，
里面大约 240 条整数指令，尾数积是用 4 次 `mul.w` 拼 16×16 部分积算的，
连 `mulh.wu` 都没用上，而 LA32R 有这条指令。

131 拍的原因是没有硬件。

### 为什么不改内核

要让 `a * b` 变快，第一条路是给 CPU 加标准的浮点扩展：改译码、
加 32 个浮点寄存器堆、处理浮点异常和状态寄存器、
在上下文切换里保存恢复浮点状态，还要改工具链才能让 GCC 发出这些指令。

这条路的问题是工作量的分布。真正跟"把乘法算快"有关的只有运算单元本身，
其余全是把它接进指令集体系的配套工作。我们要的是前者。

而且改内核会动到已经验证过的取指、译码、转发、异常通路，
这几块是整颗片子最不该动的地方。

所以不改内核。

### 于是走协处理器

这颗核本来就带一个叫 LaCC 的协处理器接口。它的形状是：

```
   两个 32 位源操作数  ---->  [ 协处理器 ]  ---->  一个 32 位结果
                              (不访存)
```

这正好是标量浮点运算的形状：`a op b` 出一个 `c`，没有别的副作用。
接口里还有一条通往 dcache 的通道，标量浮点用不上。

### 这个选择带来的约束

协处理器接在 EX 级，而且是阻塞式的：

```
   取指 -- 译码 -- [ EX ] -- 访存 -- 写回
                     |
                     +--> 发请求 ... 等 ... 等 ... 收应答
                     |
                     整条流水线停在这里不动
```

所以子单元的延迟直接就是这条指令的单价。加法器多切一级流水，
每一次浮点加法就多付一拍，没有别的指令能填进这个空档。

这跟一般的流水线设计习惯相反。平常切流水是为了提频率，
代价只是延迟变长、吞吐不变；在阻塞式协处理器后面，延迟变长就是单价变贵，
而吞吐本来就是一拍一条。

由此得到一条贯穿后面所有章节的准则：**每个子单元的延迟压到能跑出频率的最小值**。
后果有三处：比较和转换只有 1 拍（第五、六章）；
加法器被迫切三级，因为前导零计数在 20 ns 里放不下（第三章）；
五个出口的延迟不一样，分发层不做延迟对齐（本章 3.3）。

它还划出了这条路的天花板：单价再低也是"每条指令若干拍"，做不到每拍一个结果。
要吞吐得走向量引擎，那是另一个系列。

## 二、为什么是这四步

把整条链路从 C 源码画到结果返回，中间每一个环节都必须打通，
缺一个整条路就不通：

```
   C 源码    a * b
     |
     |  编译器发 bl __mulsf3
     v
   链接器    这个符号解析到谁？               <-- 环节四：软件侧替换
     |       默认解析到 libgcc，硬件就白做了
     v
   取指译码  这条指令的 op 域装得下吗？        <-- 环节一：编码空间
     |       原来只有 4 个编码，全被超越函数占了
     v
   EX 级     什么时候触发子单元？
     |       什么时候承认它吐出来的结果？      <-- 环节二：握手
     v
   协处理器  按 op 送到哪个单元？
     |       五个单元延迟不同，怎么知道该等谁？ <-- 环节三：分发与回选
     v
   写回      结果回到寄存器
```

四个环节各对应一步工作：

```
   一、扩 op 编码空间       让新指令有位置可放
   二、握手                 让一条指令只算一次、结果只收一次
   三、分发与回选           让请求找到正确的单元、结果找到正确的出口
   四、软件侧链接期替换     让已有代码不改一行就走到硬件
```

这四步跟"浮点怎么算"完全无关，一个算术公式都没有。
它们是把任何自定义运算接进这颗 CPU 都要做的事，
后面六章的运算单元全部挂在这层骨架上。

CPU 内核侧的改动只落在环节一，而且只有一个常数。

## 三、每一步做了什么

### 3.1 扩 op 编码空间

原来的 op 域宽度是按"能装 4 条指令"算出来的：

```
   改之前                          改之后

   OP_SIZE  = 4                    OP_SIZE  = 16
   OpWidth = 2                    OpWidth = 4
      |                               |
      v                               v
   +--+--+                         +--+--+--+--+
   |  |  |  4 个编码                |  |  |  |  |  16 个编码
   +--+--+                         +--+--+--+--+
    全被 exp/sin/cos/rsqrt 占满      多出 12 个位置
```

ID 到 EXE 那条总线的宽度本来就是按这个参数算的，所以它自动跟着宽 2 位，
译码级和执行级一行都没动。

真正省事的是动手前的勘察，发现三件已经做好的事：
两个源操作数早就接好了，两个操作数都已经参与转发，
官方 command 域本来就是 6 位、扩到 4 位不会撞编码。

### 3.2 握手

协处理器要回答两个问题：什么时候开始算，什么时候承认结果。

难点在于 CPU 在等应答期间会一直举着请求信号：

```
   第一条指令                        第二条指令
   |<------------------------->|<------------------------->|
   req_valid  ________________________________________________
             |                                                |
             +------------------------------------------------+
                        全程为高，中间不回落
```

如果直接拿这根线当"开始算"的信号，子单元会被反复触发，
同一条指令算很多遍。第一版用的是它的上升沿，
结果是第二条指令永远等不到上升沿，经过在第四节 4.2。

现在的做法是加一个状态位，记录"已经触发过、还没应答"：

```
   状态 = 空闲                    状态 = 在算
   +--------+                     +--------+
   |        | --- 请求有效 ----->  |        |
   |  空闲   |                     |  在算  |
   |        | <--- 应答返回 -----  |        |
   +--------+                     +--------+
        |                              |
   这时候允许触发                 这时候不再触发
                                  也只有这时候才承认子单元的结果
```

两个职责由同一个状态位承担。它为高时不再触发，所以一条指令只算一次；
只有它为高时才承认子单元的输出，所以被作废掉的运算稍后吐出来的结果不会被误收。

判断指令边界用的是"上一条已经应答"这个状态，跟信号边沿无关。

### 3.3 分发与回选

分发层按 op 把请求送到对应的单元，再把结果选回来：

```
                        op
                         |
   请求 ------------> [ 译码 ] ------+------+------+------+------+
                                     |      |      |      |      |
                                     v      v      v      v      v
                                   加减    乘     比较   转换   倒数
                                   3 拍   2 拍   1 拍   1 拍   6 拍
                                     |      |      |      |      |
                                     +------+------+------+------+
                                                   |
                        记住发的是哪个 op ------> 选一路 ----> 结果
```

五个出口的延迟不一样，而且分发层不做延迟对齐。

对齐意味着给短延迟的出口补寄存器，让它们都等到最慢那个的节拍：

```
   不对齐（现在）              对齐（没有采用）

   比较  |=|                   比较  |=|-----|
   乘    |==|                  乘    |==|----|
   倒数  |======|              倒数  |======|
         各按各的延迟出          全部拉齐到 6 拍
         单价 1/2/6              单价一律 6
```

在阻塞式接口里延迟就是单价，对齐会把比较的成本翻六倍。
所以五对信号全部平铺往上引，由上一层按 op 选。

### 3.4 软件侧链接期替换

应用代码一行不改，靠链接器把符号引到我们的实现上：

```
   改之前                            改之后

   应用   call __mulsf3              应用   call __mulsf3
             |                                 |
             v                                 v
        libgcc 的软件实现              __wrap___mulsf3
        240 条整数指令                 函数体只有一条 lacc 指令
                                             |
                                             v
                                        协处理器硬件
```

这是链接期的事，不改变代码生成。coremark、llama2、lenet、渲染器同时受益，
零适配。热点处还可以再进一步，直接用内联的 intrinsic 绕开函数调用开销，
但那要改被加速的代码。

## 四、遇到的问题

### 4.1 断言全红，失败值是 zzzzzzzz

**第一现场。** 第一次跑这一层的 testbench，19 条断言全部失败：

```
FAIL: case1 single FMUL  got=zzzzzzzz exp=40400000
FAIL: case1 single FMUL  got=zzzzzzzz exp=c2990000
FAIL: case2 back-to-back got=zzzzzzzz exp=3f800000
...
```

**解读。** 关键在 `got` 那一列的字符是 `z`。Verilog 里几个值的含义不同：

```
   0 / 1     确定的电平
   x         不定值    ——  算错了、复位没到、多个驱动源打架
   z         高阻      ——  这根线没有任何驱动源
```

19 条全部是 `z`，没有出现部分正确、部分错误的分布。
如果是运算逻辑写错了，应该拿到确定的错误数值；
如果是复位或者时序问题，应该拿到 `x`。
全部高阻意味着问题不在数据通路上，在输出端口本身：

```
   [ 运算逻辑 ] --> [ 结果寄存器 ]      ||      输出端口 --> TB
                                        ^
                                    这里断了
```

**定位。** 直接查那个输出端口有没有驱动。
重写这个模块的时候把"把结果寄存器接到输出端口"那一行弄丢了。

**修法。** 补回那一行。

**为什么判据没覆盖到。** 判据覆盖到了，一次就定位到了。
值得记的是排查顺序：模块重写之后先查每个输出端口有没有驱动，再查逻辑。
Verilog 不会为悬空输出报错，仿真器会把高阻一路传下去。

### 4.2 连着两条 lacc 指令就死锁

**第一现场。** 边沿检测那一版握手，模块级 TB 全绿，上板必死。
写了一个专门复现的 TB，激励是两条背靠背的指令，中间不放请求信号的回落：

```
inst1: rsp after 2 cyc
inst2: *** NO RESPONSE in 20 cyc — DEADLOCK
```

**解读。** 第一条正常，2 拍应答。第二条 20 拍没有任何应答，
TB 的超时计数器到顶。

这个输出排除了"算错"这一类：如果子单元被触发了，
无论算对算错，应答都会在若干拍后回来。20 拍完全静默意味着它根本没有被触发。

**定位。** 看真实波形里请求信号的形状：

```
   TB 里的激励（每次发送前先拉低）

   req  ____|~~~~|____|~~~~|____
            ^         ^
          上升沿    上升沿      两条都触发得到


   真实波形（两条指令之间不回落）

   req  ____|~~~~~~~~~~~~~~~~~~~~~
            ^
          只有这一个上升沿          第二条永远等不到触发
        |<-- 第一条 -->|<-- 第二条 -->|
```

第一条应答之后下一拍第二条就进了 EX，请求信号全程保持为高。
边沿检测再也等不到上升沿，CPU 停在 EX 级不动。

**根因。** 保持型握手信号里没有指令边界信息。
协处理器这一侧能区分"这条"和"下一条"的唯一信息是"上一条已经应答了"。

**修法。** 换成 3.2 节那个状态位。背靠背的时候状态在应答那一拍回到空闲，
下一拍第二条立刻拿到触发，一拍不损失。

**为什么判据没覆盖到。** TB 的发送任务每次都会先把请求信号拉低再拉起来。
用例的名字叫"背靠背"，但激励形态跟真实波形不一样。


### 4.3 延迟表三处是错的，而且没有判据

**第一现场。** 指令表里的延迟列长期只以注释和文档表格的形式存在，
没有任何东西在检查它。补了实测 TB 之后第一次跑：

```
=== LaCC 指令表延迟对账（in_valid -> rsp_valid）===
  FAIL: op0  EXP    延迟 T+7，指令表/真源说 T+4
  FAIL: op1  SIN    延迟 T+3，指令表/真源说 T+4
  FAIL: op2  COS    延迟 T+3，指令表/真源说 T+4
  PASS: op3  RSQRT  延迟 T+7
  PASS: op4  FADD   延迟 T+4
  ...
  FAIL: op13 FRECIP 延迟 T+7，指令表/真源说 T+4
================================================
lacc 延迟 TB: 17 PASS, 4 FAIL
HAS FAILURES
```

**解读。** 四条 FAIL 对应三处错误，sin 和 cos 是同一处。

三处的方向不一样：exp 和 frecip 是**实际比表里写的慢**，
sin 和 cos 是**实际比表里写的快**。

```
   表里写的     实际
   exp    T+4    T+7     慢 3 拍
   sin    T+4    T+3     快 1 拍
   cos    T+4    T+3     快 1 拍
   frecip T+4    T+7     慢 3 拍
```

方向不一致这一点排除了"整表偏移"这类系统性错误
（比如口径从"子单元延迟"变成"对外延迟"时忘了统一加一），
说明四个数是各自独立写错的，来源是各改各的时候没有同步这张表。

**影响面。** 延迟列不是文档装饰。渲染加速器里的影子流水是照着这个数配的，
错一拍就是功能错。

**修法。** 把延迟从注释变成实测量加断言，11 条 op 全测，
包括未分配 op 的兜底路径。

这些数现在各有一处定义：`sfu/` 四条在 `rtl/sfu_lat.vh`，
`fp/` 五条在 `rtl/fp32_lat.vh`，协处理器顶层多出的那一拍在
`lacc_defs.vh` 的 `LACC_RSP_REG_LAT`。指令表、TB 的期望值、
以及下游按延迟配的影子流水都从这三处取值。

`fp/` 那五条另有一层例化期检查：分发层用条件 generate 约束它们为正，
乘累加单元用同样的写法约束标记链深度不小于 2。这一层管的是常数之间的关系，
实测偏差仍然只有 TB 能发现，两层各管一半。

**为什么判据没覆盖到。** 没有判据。写在注释里的事实断言，
只有在有 TB 断言它的地方才靠得住。

## 五、结果

骨架接通之后，六条 FP 指令的位置是这样的：

| op | 助记 | 计算单元 | 对外延迟 |
|---:|---|---|---:|
| 0–3 | EXP / SIN / COS / RSQRT | `sfu/` | T+6 / T+3 / T+3 / T+6 |
| 4 | FADD | `fp32_add` | T+4 |
| 5 | FSUB | `fp32_add`（翻 rk 符号位）| T+4 |
| 6 | FMUL | `fp32_mul_pipe` | T+3 |
| 7 | 未分配 | 兜底 qNaN | T+2 |
| 8 | FCMP | `fp32_cmp` | T+2 |
| 9 | FCVT | `fp32_cvt` | T+2 |
| 13 | FRECIP | `fp32_recip` | T+6 |

对外延迟 = 子单元延迟 + 1，多的那一拍是协处理器顶层的输出寄存器。

op 编码的唯一真源在 RTL 和 BSP 头文件两处，中间有编译期断言对账。
op 7 空着，它是 testbench 里"未实现 op 兜底"用例的靶子，
占用了那条用例会假 FAIL。

这一章本身不产生性能数字，它产生的是后面六章的接入点。
