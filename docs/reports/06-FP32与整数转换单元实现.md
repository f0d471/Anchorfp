# FP32 与整数转换单元实现

## 一、动机

比较做完之后再拆一次账，最费时的两段的名字直接给出了下一个目标：
`quant` 和 `dequant`。两段加起来 626 ms，占 geometry 的 42.8%，
而且是上一个工作点降幅垫底的两段——别的段都因为比较变快而下降，
这两段几乎没动。

名字就是量化和反量化，主体是 int 和 float 互转，
编译出来是 `__floatsisf` 和 `__fixsfsi`，软件版 55.76 拍和 27.93 拍。

这两条的电路深度都不大，按延迟准则应该跟比较器一样做成 1 拍。

## 二、为什么两个方向的步骤不对称

### 两种编码的差别在于小数点的位置

int32 和 fp32 都是 32 位，装的都是一个数，区别在于小数点在哪：

```
   int32     小数点固定在最低位右边，每一位的权重是写死的

             b31 b30 ... b1 b0 .
              |               |
             2^31            2^0

   fp32      小数点位置由阶码给出，浮动

             1 . f f f f f f f  x  2^(e-127)
                                     |
                                  这个决定小数点挪到哪
```

互转就是在这两种编码之间搬运有效位。搬的时候要回答一个问题：
**有效位现在在哪、应该挪到哪。** 两个方向对这个问题的处境不同，
步骤的不对称就是从这里来的。

### i2f：位置未知，要先找

给一个整数，它的最高有效位在第几位是不确定的：

```
   00000000 00000000 00000001 01101101      最高位在 bit8
   00000000 01101101 00000000 00000000      最高位在 bit22
   01101101 00000000 00000000 00000000      最高位在 bit30
```

而 fp32 要求最高有效位固定放在隐藏位那个位置。所以第一件事是**找**：
数出前面有多少个零，才知道要左移多少位。

找到之后，"找到的位置"本身就是阶码——最高位在第 k 位，
这个数的量级就是 `2^k`，阶码是 `k + 127`。

再往后还有一件事：整数最多有 32 位有效，而 float 只能存 24 位。
超过 `2^24` 的整数转过去必然丢低位，所以要**舍入**。

```
   i2f 的四步

   取绝对值  ->  找最高位  ->  左移到位、算阶码  ->  舍入
                  ^                                   ^
              位置未知，要找                    32 位装不进 24 位
```

### f2i：位置已知，但范围有限

反方向，阶码直接把小数点位置告诉你了，移位量是算出来的，不用找：

```
   移位量 = (阶码 - 127) - 23
             |            |
             真实指数      隐藏位在尾数里的位置

   结果为正 -> 左移（这个数比 2^23 大）
   结果为负 -> 右移（这个数比 2^23 小，右移会丢小数部分）
```

不用找，所以省掉了 i2f 的第二步。

但 int32 没有阶码，能表示的范围是死的。一个 float 很容易超出去：

```
   float 能表示的范围        int32 能表示的范围

   +-3.4e38                  +-2.1e9
   |<--------------------->|  |<-->|
                               ^
                        超出这个范围的输入无法表示
                        必须决定给什么答案
```

所以 f2i 多出一步**饱和**：超上界给最大值，超下界给最小值。
无符号还要额外处理负输入。

另外截断的方向也是定的：C 语言的 `(int)` 语义是向零截断，不是舍入。
所以 f2i 没有舍入这一步。

```
   f2i 的四步

   拆包补隐藏位  ->  算移位量、移位  ->  向零截断  ->  范围判断与饱和
                       ^                  ^              ^
                  位置已知，算出来      C 语义要求      int32 范围有限
```

### 两个方向的对照

```
                 i2f                      f2i
   位置          未知，要找前导零           已知，由阶码算出
   精度          32 位装不进 24 位，要舍入   向零截断，C 语义
   范围          整数一定装得进 float       float 可能装不进整数，要饱和
```

再加一件公共的：把两个方向合并成一个 op。

## 三、每一步做了什么

### 3.1 两个方向合并成一条指令

i2f 和 f2i 共用一个 op，靠立即数区分：

```
   +-------+--------+
   |  op9  |  imm   |
   +-------+--------+
               |
               +-- imm[0] = 0  ->  i2f
               |   imm[0] = 1  ->  f2i
               +-- imm[1] = 0  ->  有符号
                   imm[1] = 1  ->  无符号

   四种组合，一个 op 号
```

这是[第五章](05-FP32比较器的三态编码与NaN语义.md)那个立即数手法的第二次使用。

合并还有个实际好处：两个方向的组合逻辑深度都不大，共用一级输出寄存器，
全 SoC 只有一份，加起来才三百多个 LUT。

### 3.2 i2f：找最高位

对整数做的事：

```
   输入     00000000 01101101 xxxxxxxx xxxxxxxx
                     ^
                  最高位在 bit22
                     |
                     v  数出前面有 9 个零
   左移 9 位后
            01101101 xxxxxxxx xxxxxxxx 000000000
            ^
            最高位挪到 bit31，也就是隐藏位该在的位置

   阶码 = 22 + 127 = 149
        = 158 - 9
          ^     ^
       常数   前导零数
```

那个常数 158 是 127 加 31：最高位在 bit31 时量级是 `2^31`，
阶码应该是 158。前导零每多一个，阶码减一。

找最高位这件事写成 32 路并列判断，跟加法器里那个前导零计数
（[第三章](03-FP32加法器的三级流水实现.md) 3.2）是同一类电路。

### 3.3 i2f：舍入

左移到位之后，低位有一段装不进 24 位尾数：

```
   +------------- 24 位尾数 -------------+------ 装不下 ------+
   | 1 . f f f f f f f f f f f f f f f f | x x x x x x x x x |
   +-------------------------------------+-------------------+
                                           ^
                                     GRS 三位判进位
```

用的还是 GRS 那套（[第二章](02-FP32乘法器的流水与舍入实现.md) 3.5）。

这里的舍入是真的会发生的：32 位整数最多需要 24 位尾数才能精确表示，
超过 `2^24` 的整数一定丢低位。

### 3.4 f2i：移位与截断

阶码给出小数点位置，按它把尾数挪到整数该在的位置：

```
   输入是 5.75  ->  1.0111 x 2^2

   补隐藏位后的尾数（24 位，隐藏位在最高）
   +-+-----------------------+
   |1|0111000...             |
   +-+-----------------------+
      |
      v  按阶码算出的量移位，让隐藏位落到 2^2 的位置
   +------------------+-------------+
   |     整数部分 101  | 小数部分 11 |
   +------------------+-------------+
                        |
                        v  向零截断，直接丢掉
                       101  = 5
```

采用向零截断，以符合 C 语言 `(int)` 的转换语义。

### 3.5 f2i：范围判断与饱和

超出 int32 范围的输入要给一个确定的答案：

```
   输入            有符号            无符号
   ----------------------------------------------------
   |x| < 1         0                 0
   正的超上界      0x7FFFFFFF        0xFFFFFFFF
   负的超下界      0x80000000        0
   负数（不超）    正常转换           0        <- 无符号额外钳位
   NaN             0                 0
```

有符号和无符号的上界差一档阶码：有符号能装到 `2^31 - 1`，
无符号能装到 `2^32 - 1`。

`INT_MIN` 那个点单独验过：它走饱和分支，饱和值恰好就是 `0x80000000`，正确。

整个模块只有移位和加减，一个乘法器都没有。

## 四、遇到的问题

### 4.1 随机激励的 bit31 恒为 0

**第一现场。** 统计生成出来的向量，bit31 的分布是：

```
   5 万条随机向量中
   bit31 = 0 :  49998
   bit31 = 1 :      2
```

**解读。** 对这个模块，bit31 是符号位。

```
   受影响的路径

   i2f  负整数           要走取绝对值那一支     几乎没执行过
   f2i  负浮点           要走符号恢复那一支     几乎没执行过
   f2i  无符号 + 负输入  要走钳零那一支         几乎没执行过
```

三条路径在随机段里几乎全是空转，全靠定向用例撑着。
而"随机 5 万条全过"这句话读起来像是覆盖得很好。

**定位。** 随机数来自 `rand_r()`，它的返回范围是 `0` 到 `2^31 - 1`，
也就是 bit31 恒为 0。那 2 条是从别的路径混进来的。

```
   期望的取值域             实际的取值域
   [0, 2^32)                [0, 2^31)
   |<------------->|        |<------>|
                                     ^
                              一半的空间从来没被采样
```

**修法。** 改成拼两次取满 32 位重新生成。改完 bit31 为 1 的有 49,861 条，
仍然全对，设计确实没问题。但在修之前，这件事是不可知的。

**方法。** 随机激励的取值域要单独验一次。
C 标准只保证 `rand()` 返回 `0` 到 `RAND_MAX`，而 `RAND_MAX` 通常是 `2^31 - 1`。

### 4.2 RTL 全对，板上收益是零

**第一现场。** RTL 写完，仿真 36 条定向加 100,067 条金标准全过，bin 也编出来了。
板上探针打印：

```
__floatsisf     55.75
__fixsfsi       27.93
```

跟改之前一模一样。

**解读。** 这个输出的信息量在于它"太正常"：

```
   如果硬件通路接错了      -> 结果数值错，判据会红
   如果硬件通路接上了      -> 单价应该掉到个位数
   如果硬件通路没接上      -> 走回软件，单价就是软件的那个数

   拿到的正是软件的数，而且一位不差
```

所以硬件根本没有被调用过。

**定位。** 顺着调用链倒查：

```
   应用   call __floatsisf
            |
            v
   链接器决定这个符号解析到谁
            |
            +-- 应该解析到 __wrap___floatsisf   （我们的）
            |
            +-- 实际解析到 libgcc 的版本         （查 elf 符号表看到的）
```

根因是两个 Makefile 的硬件开关分支里漏了四条链接选项，
少了 `--wrap=__floatsisf`、`--wrap=__floatunsisf`、
`--wrap=__fixsfsi`、`--wrap=__fixunssfsi`。

没有这四条，那四个 `__wrap___*` 函数只是被定义了，不会被链接进 elf。

**修法。** 补上这四条。

**为什么判据没覆盖到。** 判据全在被测代码那一侧：

```
   RTL         金标准对拍      对的
   软件 wrapper 函数体          对的
   构建配置     链接选项        <-- 缺口在这里，没有任何判据看它
   探针         照常打印一个合法的数，不会报错
```

这是同一个坑的第三次。前两次分别是边界用例全用字面量被 GCC 常量折叠掉
（被测的那一侧全程没上场），和少写一种调用形态导致某个分支从没被测到。
共同的形状是：判据的最后一公里在构建配置里，不在被测代码里。

## 五、结果

| | 软件 libgcc | 硬件 |
|---|---:|---:|
| `__floatsisf`（i2f）| 55.76 拍 | 3.99 拍 |
| `__fixsfsi`（f2i）| 27.93 拍 | 3.99 拍 |

3.99 拍是这批指令里最快的，因为转换单元只有 1 拍延迟，
剩下的全是调用开销。

geometry 从 1,461 ms 降到 1,193 ms，少了 18.4%。
事前的量化预判是 12.0%，实测超了一半。

有个复合探针提供了独立佐证。`i2f + *const` 这个组合操作，
改之前 61.74 拍，其中 i2f 单项就占 55.75，
也就是转换占了整个操作的 90%，乘法只占 8%。改之后这个组合降到 9.99 拍。
`quant` 和 `dequant` 的内循环正是这个形状。

至此转换的占比从 13.9% 降到 1.7%。
