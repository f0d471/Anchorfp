# FP32 加乘单元的 FTZ 语义实现

## 一、动机

### 硬件很快，应用看不到

乘法和加法上板之后，硬件本身的延迟已经压到了预算内：乘法 2 拍、加法 3 拍。
但探针量出来的应用侧单价对不上：加法 23.49 拍，减法 25.49 拍。

多出来的十七八拍不在硬件里，在 wrapper 里。

拆开量了一次，把 wrapper 的总开销减去裸硬件调用的开销：

| | wrapper 总开销 | 硬件延迟 | 差值 = 软件分类 |
|---|---:|---:|---:|
| `__addsf3` | 23.49 | 6.98 | 16.5 |
| `__subsf3` | 25.49 | 6.99 | 18.5 |
| `__mulsf3` | 10.99 | 5.98 | 5.0 |

软件分类判据比硬件本身贵 2.4 倍。

### 那十七八拍在做什么

当时的调用路径是这样的：

```
   应用调 __addsf3
        |
        v
   +----------------------------+
   | wrapper                    |
   |   操作数是 denormal 吗？    |
   |   操作数是 Inf 吗？         |
   |   两个 Inf 异号吗？         |
   |   结果会下溢到 denormal 吗？ |
   +----------------------------+
        |                    |
   四条都不命中            任一条命中
        |                    |
        v                    v
    发 lacc 指令        跳回 libgcc 软件实现
    （3 拍）             （81 拍）
```

这么写的原因是硬件当时不处理 denormal，行为跟 IEEE 不一样，
所以软件要把这些输入排除在硬件通路之外。

### 结论

判据本身是必要的，位置错了。它判断的是"这个输入硬件能不能算"，
这件事硬件自己在拆包那一拍就能判完，放在软件里要花十几条整数指令。

所以这一章不改任何算术，只把语义边界从软件挪进硬件。

## 二、为什么是这七步

### 一个语义改动会波及哪些地方

FTZ 改的是一件事：**"零"的定义**。原来只有阶码全零且尾数全零算零，
改完之后阶码全零就算零，不管尾数。

一旦"零"的定义变了，凡是跟零有关的判断点都要跟着变。
把这些点找齐，步骤就出来了：

```
   浮点数进入硬件
        |
        +-- 拆包时判断它是不是零 -----------> 点 1：输入侧
        |
        +-- 特殊值判断里用到"是不是零"
        |   （Inf x 0 = NaN 这条规则）------> 点 2：衍生契约
        |
        +-- 主运算（不涉及零的定义）
        |
        +-- 组装时判断结果是不是太小 -------> 点 3：输出侧
        |
        v
   结果出去

   另外还有两个不在这条通路上、但共用同一套契约的地方：
        比较器也要判"是不是零"  ------------> 点 4
        软件 wrapper 里的四条判据 ---------> 点 5：删掉
```

前三点是加法器和乘法器内部的，第四点是比较器，第五点在软件侧。

### 再加两步

**定语义。** 选 FTZ 之前要先确认它是标准允许的取舍，
并且写清楚代价，否则后面所有偏差都没有依据。

**收副产品。** FTZ 之后进入主通路的操作数必然是规格化数，
这会让乘法器的一条分支变成死码。这是语义改动的连带结果，
一并清除。

### 七步

```
   一  定语义        决定对 denormal 采取什么行为，写清代价
   二  输入侧        拆包时把 denormal 当零
   三  输出侧        结果落进 denormal 区间时写零
   四  衍生契约      凡是用到"是不是零"的判断跟着改
   五  同步比较器    让四个消费者用同一套契约
   六  清空 wrapper  软件侧四条判据全删
   七  收副产品      删掉因此变成死码的模块
```

## 三、每一步做了什么

### 3.1 定语义：FTZ 是什么，代价是什么

阶码为 0 的时候，格式的解释规则改变：隐藏位不再是 1 而是 0，
表示的值是 `0.f × 2^-126`。这类数叫 denormal：

```
   数轴（只画正半边，靠近零的部分）

   0        denormal 区间          最小规格数
   |----|----|----|----|----|--------|=============>
   |    间隔均匀的一小片              |  常规数
   |                                 |
   +--- 填补 0 和最小规格数之间的空隙  1.18e-38
```

它用于实现渐进下溢，避免结果在阈值处直接截断为零。硬件支持它的代价是：
输入端要判断隐藏位取哪个值，加法要处理"尾数没有前导 1"的对阶，
输出端下溢时要做前导零计数、变长右移、阶码修正。

FTZ 的做法是把这一整片区间直接压到零：

```
   开 FTZ 之后

   0        denormal 区间          最小规格数
   |<-------- 全部当成 0 --------->|=============>
```

x86 有 `MXCSR.FTZ/DAZ`，ARM 有 `FPSCR.FZ`，GPU 基本默认开着，
资源受限的嵌入式 FPU 常常只有这一种模式。这是标准里允许的取舍。

代价写清楚：绝对值小于 1.2e-38 的中间结果会变成 0。
我们跑的负载是神经网络推理和三维渲染，这个范围没有意义。

### 3.2 输入侧

拆包的时候多一个判断，阶码全零就把尾数整个置零：

```
   常规数        e != 0                denormal / 零   e == 0
   +-+------+------------+             +-+------+------------+
   |s|  e   |     f      |             |s|  0   |     f      |
   +-+------+------------+             +-+------+------------+
              |                                   |
              v  补隐藏位 1                        v  尾数直接清零
   +-+------+-+------------+           +-+------+-+------------+
   |s|  e   |1|     f      |           |s|  0   |0|   全 0     |
   +-+------+-+------------+           +-+------+-+------------+
```

一个判断同时处理了 ±0 和 denormal 两种情况，因为它们在 FTZ 下行为相同。

### 3.3 输出侧

组装的时候看最终阶码落在哪一段：

```
   最终阶码   <= 0        1 .. 254       >= 255
              |            |              |
              v            v              v
           写正负零     正常组装      写正负无穷
              ^
        原来只有 == 0 才算下溢
        现在整段 <= 0 都写零
```

判据从"等于 0"改成"小于等于 0"，因为阶码中间量是 10 位带符号的，
下溢会算出负数（[第二章](02-FP32乘法器的流水与舍入实现.md) 4.2）。

### 3.4 衍生契约

这一步容易漏。乘法器里有一条规则是 `Inf × 0 = NaN`，
它依赖"是不是零"这个判断。FTZ 把 denormal 变成了零，
所以 `Inf × denormal` 也必须落进这条：

```
   改之前                            改之后

   Inf x 0          -> NaN           Inf x 0          -> NaN
   Inf x denormal   -> Inf           Inf x denormal   -> NaN
                       ^                                 ^
              按 IEEE 是对的            因为 denormal 已经是零了
```

不跟着改的话，同一个操作数在乘法器的两个判断点上，
一边说它是零、一边说它不是零。

### 3.5 同步比较器

比较器的入口做同样的规整。这一步跟性能无关，目的是让四个消费者
（CPU、矩阵加速器、渲染加速器、向量引擎）用同一套契约：

```
   不同步的后果

   同一个 denormal 值 d
        |
        +--> 比较器说   d != 0
        |
        +--> 乘加器说   d == 0

   同一个程序里，两个模块对同一个数给出矛盾的答案
```

细节在[第五章](05-FP32比较器的三态编码与NaN语义.md)。

### 3.6 清空 wrapper

硬件接管语义之后，调用路径变成：

```
   应用调 __addsf3
        |
        v
   +----------------+
   | wrapper        |
   |   一条 lacc    |
   |   一条返回     |
   +----------------+
        |
        v
    协处理器硬件
```

四条判据全删。

### 3.7 收副产品

FTZ 之后进入常规通路的操作数必然是规格化数，尾数落在 `[1, 2)`。
两个这样的数相乘，积落在 `[1, 4)`：

```
   积的可能范围              需要的规格化动作

   [1, 2)                    不动
   [2, 4)                    右移 1 位
   (0, 1)                    左移若干位   <-- FTZ 之后不可能发生
```

也就是说乘法器的左移分支永远走不到。
原来处理左移的是一个独立模块，48 位宽、6 路的移位选择器，
被例化了 47 份（32 路 MAC 阵列加上渲染加速器里的十几个乘法器）。删掉之后：

| | 删之前 | 删之后 |
|---|---:|---:|
| Slice LUTs | 74,021 | 66,658（−9.9%）|

## 四、遇到的问题

### 4.1 过 wrapper 比直接调裸硬件还快

**第一现场。** 改完之后 `softfp_prof` 打出的两行：

```
__addsf3        5.99
hw_faddf        6.98
```

上面一行是过 wrapper 的路径，下面一行是直接调裸硬件函数。
绕一层反而快了 0.99 拍。

**解读。** 物理上不可能：

```
   裸硬件路径     |-- 协处理器 --|
   wrapper 路径   |-- 调用 --|-- 协处理器 --|-- 返回 --|

   后者是前者加上两段，只可能更长
```

所以这 0.99 拍是测量本身带进来的，不是被测对象的差异。

**定位。** 探针的做法是"跑紧循环，减掉空循环基线"。
看两段探针的循环体：

```
   段 A（__addsf3）      编译器直接生成 bl，循环体 N 条指令
   段 B（hw_faddf）      调的是汇编文件里的独立函数，循环体 N+1 条指令

   两段的空循环基线不同，而探针减掉的是同一个基线
```

**结论。** 0.99 拍是两段探针的循环体差异。
正确的读法是两者已经落进测量分辨率之内，
也就是软件分类开销归零，这正是这个工作点的目标。

**记一笔。** 出现"物理上不可能"的数时，先怀疑测量口径，再怀疑实现。
探针的基线必须跟被测循环体同构。

### 4.2 删逻辑之后时序余量下降

**第一现场。** 删掉那个左移模块省了 7,363 个 LUT，
当时的预期是逻辑少了、布局松了，时序余量应该回来一些。CI 报告给出的是相反的结果。

完整数据和分析在[第九章](09-FP32数据通路的hold时序修复.md) 4.3，
那里还有另外三轮 CI 的对照。

**解读要点。** 任何大幅改变网表的改动都会触发重新布局，
余量随之重新分配。"删逻辑等于给余量"这个直觉不成立。

## 五、结果

三个 wrapper 的单价：

| | 挪之前 | 挪之后 |
|---|---:|---:|
| `__addsf3` | 23.49 | 5.99 |
| `__subsf3` | 25.49 | 5.99 |
| `__mulsf3` | 10.99 | 4.99 |

geometry 那一级从 2,621 ms 降到 1,662 ms，少了 36.6%。
这个工作点一行 RTL 算术都没改。

板上跑了 31 条边界自检，全过：FTZ 三条、Inf 五条、乘法九条
（含 `Inf*0`、`Inf*dmin`、`(-dmin)*2 = -0` 这条负 denormal 保符号的）、
零符号四条、qNaN 传播两条，加上 16 对随机值的逐位扫描。

`tb_fp32_denorm` 的两个计数曾记录为 161/80，正确基线应为 173/110，
当时那 12 条和 30 条不符被解释成"FTZ 语义下的正常基线"。
金标准按 FTZ 契约重写之后两边都是全过，
所以现在这两个数字报错就是真缺陷，不能再解释成基线。
