# 不改结构的面积回收

## 一、动机

[第十章](10-FP32乘累加换成定点窗口累加器.md)把 `fp32_mac_unit` 的累加器换成定点窗口形态，
反馈环压到一拍，代价是面积：整机 LUT 从 64890 涨到 81729，
乘累加阵列 `gemm_pe_array` 独占 39781，占整机的 48.7%。
精度那一侧的账在[第十一章](11-定点窗口累加器的误差边界.md)结清，这一章结面积的账。

先确认打哪儿。同一次实现的 WNS 为 +0.460 ns，最差路径落在向量引擎的地址生成器上，
不在 MAC。所以这一轮只回收面积，时序留作预算：只要不把关键路径弄坏，写法可以随便动。

同一轮要回答的还有一个问题：这个模块 597 行是否过大、该不该拆。

动手之前先排除一份错误的现状。`Main/fpga/` 下曾有三份报告
（`rt_full` / `rt_summary` / `rt_util`）显示 WNS 为 -4.663 ns、1810 个失败端点、
最差路径在 `PE_LANE[11].u_mac`。那次运行被 Vivado 的自动增量综合骗过：
第十章新加的两级流水一个都没进网表，报告描述的是改动之前的锥子。
三份已移入 `Main/fpga/stale-reports/` 并附了说明。照它们判断，
会得到「MAC 时序崩了」这个反向结论，靶子从一开始就打错。

## 二、为什么是这四条

不动结构、不动语义的前提下，一条已经工作的数据通路上能回收的面积只有三类来源：

| 来源      | 形态                     | 对应的工作点 |
| ------- | ---------------------- | ------ |
| 寄存器位宽   | 寄了下游用不到的位              | A      |
| 控制集     | FF 数不变，复位与使能网的接法决定打包密度 | B、D    |
| 组合逻辑的形状 | 功能确定而综合结果由写法决定的那一段     | C      |

四条都是逐位等价的：改完之后硬件行为一位不变，逐位金标准与集成级判据照常通过。
其中 A、B、C 单 lane 离线综合就能量出来，D 只有整机才看得见，原因见 4.2。

另有两个「看起来应该更好」的改法改到了结构与语义上，单列在第四节，实测都判死。
还有一条评估之后不做：`rescale` 的档位数 `DMAX` 为 6，而 `d_idx` 是 3 位、能表示 8 档，
理论上省得掉一层多路器；收益是个位数 LUT，代价是把一个由参数算出来的量写死，不划算。

## 三、每一步做了什么

### 3.1 白嫖 A：规格化结果只寄 26 位

`n2_mn` 原来把整条 `AccW = 88` 位的规格化结果寄进最后一级。
而末项舍入只用得到三样东西：

```
   位序  87                     64  63                            0
         |      高 24 位          | g |          其余 62 位          |
              进最终尾数            ^                  ^
                            决定进位方向         只需要它们的或
```

于是这一级只寄高 24 位、guard 位与一位粘滞位，共 26 位。
其余 62 位的或归约提到上一级去做，与放在下一级做是同一份逻辑，位置换了而已。

单 lane 省 62 个 FF，32 条 lane 就是 1984 个。

### 3.2 白嫖 B：数据路径寄存器不接复位

流水线寄存器分两种：跟着数据走的，和跟着控制走的。A 级与 B 级原来由一个复位块统管两种。
拆成两个 `always`，数据位一个（无复位），随行的有效位与末项标记一个（有复位）：

```verilog
    // 改动前
    always @(posedge clk) begin
        if (!rst_n) begin
            a1_valid <= 1'b0;  a1_last <= 1'b0;
            a1_mant  <= 48'd0; a1_sh   <= {ShAmtW{1'b0}};   // 数据位也接了复位网
            ...
        end else begin ... end
    end

    // 改动后
    always @(posedge clk) begin                 // 数据位
        a1_mant <= mant_in;  a1_sh <= sh_now;  a1_sign <= sign_in;
        a1_d    <= d_idx;    a1_clr <= raise_clr;
    end
    always @(posedge clk) begin                 // 控制位
        if (!rst_n) begin a1_valid <= 1'b0; a1_last <= 1'b0; end
        else        begin a1_valid <= fire_in; a1_last <= t_last; end
    end
```

这么做的理由要写进注释，不能只说省资源。下游看这一级只经 `a1_valid` 与 `a1_last`
两个门：累加器的更新条件是 `term_v`，溯上去就是 `a1_valid`，复位期间恒零，
所以数据位里是什么都进不了任何状态。

FF 数一个没变，变的是控制集。7 系列一个 slice 里的 8 个 FF 必须共用同一组时钟、
复位与使能，复位网少接一路，打包密度就松一点。单 lane 实测省 32 个 LUT。

模块输出 `mac_out` 保留复位：它的值会传到结果总线上，复位后取 X 不合适。

这一刀当时只覆盖了 A、B 两级。Na、Nb 两级看着像是本来就对，实际问题更严重，见 3.4。

### 3.3 白嫖 C：前导零检测改成两级

原来是一条 `AccW` 级的链：由低到高扫，遇到 1 就记下位序，后写者胜，
扫完就是最高置位的位置。功能没错，写法也与 `fp32_add` 里的规格化扫描一致。
问题是它的形状不确定：88 级级联多路器综合成什么完全看工具，
而这条链正好挂在 88 位取模加法器后面，是这一级最长的一段。

改成两级，组数与组宽都是常量，形状是定的：

```
   acc_mag  |  组 10  |  组 9  | ... |  组 1  |  组 0  |     每组 GrpW = 8 位
                |         |             |         |
                +---------+-- 组内求或 --+---------+
                              |
                       11 位组标志 lz_gnz
                              |
                    优先编码 -> lz_gsel（最高的非零组）
                              |
                    组内优先编码 -> lz_bsel（组内最高置位）
                              |
                  {lz_gsel, lz_bsel} 即最高置位的位序
```

这里有个坑值得记：拼接结果直接赋给 `ShAmtW` 位的线，
在 `GIdxW + 3` 恰好等于 `ShAmtW`（当前参数下就是）时会写出一个 0 宽度的填充，那是非法的。
先拼给一条更宽的线 `lz_pos`，零扩展交给语言做。

### 3.4 白嫖 D：Na 与 Nb 两级，把复位从时钟使能里拆出来

这一条由布线报告逼出来，发现过程写在 4.1，这里只写修法。

Na 级原来只给 `n1_go` 一个复位值，其余十来个数据寄存器都落在 `else` 分支里。
乍看是 3.2 那个规矩，实际相反：数据寄存器在复位期间保持不变，
而保持不变正是时钟使能的语义，于是综合器把 `rst_n` 接成了这一整组寄存器的 CE。

```verilog
    // 改动前：rst_n 成了 n1_mag 等十来个寄存器的 CE
    always @(posedge clk) begin
        if (!rst_n) n1_go <= 1'b0;
        else begin
            n1_go  <= acc_last_q;
            n1_mag <= acc_mag;
            ...
        end
    end

    // 改动后：控制位一个块带复位，数据位另一个块无条件更新
    always @(posedge clk) begin
        if (!rst_n) n1_go <= 1'b0;
        else        n1_go <= acc_last_q;
    end
    always @(posedge clk) begin
        n1_mag <= acc_mag;  n1_lz <= lz_c;  n1_sign <= acc_neg;
        ...
    end
```

功能等价：复位期间 `n1_go` 恒零，下游不看这些数据位；`acc_val` 自身有复位，
所以 `n1_mag` 在复位期间取到的是零。Nb 级同样处理。

### 3.5 只拆断言，不拆主数据通路

回到「597 行该不该拆」。主数据通路不拆，依据三条：

1. 共享桶形右移器横跨 A 级与 Nb 级。按流水级拆模块，就得把移位器提成独立模块
   再加一层仲裁接口，面积不变而接口复杂度上升，还把「为什么能共享」这个论点
   从代码里赶走。4.4 那个实验刚好证明共享是对的，这个论点值得留在原地。
2. 数据通路按流水级切分本身是反模式：A 到 B 一级要传 mant / sh / sign / valid /
   last / d / clr 七组信号，而综合器看不见跨模块的常量传播。
3. 横向对照，`cvfpu` 的 `fpnew_fma.sv` 是同一量级的单文件数据通路，
   业界没有把它按级拆开的做法。

做了一处轻拆：仅仿真的契约断言外提到 `rtl/fp32_mac_assert.vh`（102 行），
主文件里只剩几行 include，597 行降到 531 行，剩下的全是数据通路，
契约变更的 diff 也不再混在数据通路的改动里面。

外提前后单 lane 综合的三个数一位没变，这本身就是「`ifndef SYNTHESIS` 那段确实不进网表」
的一条证据，比在文档里声明一句强。

特殊值旁路的拆分（约 35 行，原本评估过拆成 `fp32_mac_special.v`）没做。
收益只是可读性，代价是新增一个综合源文件，而本仓新增源文件必须重跑
`create_project.tcl` 重建 Vivado 工程（文件列表是创建时的快照）。
它与 `f_nz` / `f_zsgn` 的语义和末项组装也是紧耦合的，拆出去要把 6 个 sticky 位当端口传。

## 四、遇到的问题

### 4.1 面积降了，WNS 从 0.460 掉到 0.053

三条白嫖做完，面积如愿降了，整机 WNS 却掉到 0.053 ns。
改动全是逐位等价的、面积还在减，时序反而变差，这在本仓不是第一次
（[#17]「删逻辑不等于给余量」），但这次追下去有额外收获。

第一现场，布线后的最差路径（`Main/fpga/rpt3.tcl`）：

```
   slack = 0.053   levels = 0
   from  pll_clk.u_rst_sys/delay_reg[1]/C
   to    u_gemm_top/u_mac/u_pe_array/PE_LANE[18].u_mac/n1_mag_reg[11]/CE
```

解读：`levels = 0` 说明起点到终点之间没有一级组合逻辑，整条 slack 都花在布线上；
终点是 CE 脚而不是 D 脚，说明这条路径喂的是时钟使能；
起点是复位同步器的输出。三样凑一起，这是复位网，与数据通路无关。

定位：回去看 Na 级的写法，`n1_mag` 等十来个数据寄存器落在 `else` 分支里，
复位期间保持不变，综合器据此把 `rst_n` 综合成它们的 CE。
88 位乘 32 条 lane，几千个 CE 端全挂在复位同步器的一个输出上，扇出到这个量级，
布线延迟自然吃掉整条余量。修法见 3.4。

原判据为什么没覆盖到它：3.2 那一刀当时看到 `n1_*` / `n2_*` 只复位 `n1_go` / `n2_go`，
判断它们「本来就是对的写法」，还把这个判断写进了文档。
两种写法的区别在于复位期间数据位是被清零还是被保持，
前者接的是复位网，后者接的是使能网，后者更糟。
判据这一侧则是另一回事，见 4.2。

### 4.2 这一条单 lane 综合量不出来

单 lane 离线综合在白嫖 D 前后是 1275 与 1277 个 LUT，差 2 个，在噪声里。
一条 lane 只有 88 个 CE 端，不构成高扇出，问题在这个尺度上不存在。

这件事值得单记一笔：离线单模块综合看不见高扇出网络问题。
凡是「一个信号扇到几千个端」的毛病，只能在整机层面量，
而且往往要等到布线之后才看得见，布局前的估计里这种路径的延迟是猜的。

### 4.3 那 0.407 ns 到底算谁的

整机 WNS 在这一轮里从 0.460 掉到 0.054，不能一股脑记在这几工作点头上，分两半：

- 改动前那次的最差路径在向量引擎的地址生成器上（0.460），
  说明当时 CPU 那条 TLB 到 EXE 的路径 slack 大于 0.460。
  现在同一条 CPU 逻辑掉到 0.054，而 CPU 这一轮一行没改，
  这一段是重建工程之后布局重来的结果。
- 第一轮里 MAC 的 CE 路径确实并列榜首（0.053），这一条由写法造成，
  白嫖 D 把它推到 1.550，这一段是这一轮改掉的。

要严格分离两者，得把 RTL 回退到改动前、用同样的重建流程再跑一次做对照。
这一轮没跑，所以上面的归因是靠落点推断的，不是对照实验的结论。
谁要拿这个 WNS 当基线，先看这一段。

### 4.4 拆开共享的桶形移位器，实测判死

对齐与规格化现在共用一个 88 位右移器，规格化那一侧靠输入输出两端的位序翻转
把左移做成右移，翻转是纯连线，不要钱。共享省了一个移位器，
代价是对齐那一侧也被迫用满 88 位：`al_pre` 的低 32 位与高 8 位恒零，
却因为另一路是满宽而没法常量传播。那么拆成两个专用移位器，会不会因为对齐侧变窄而净省？

| 档 | LUT | FF | WNS |
|---|---:|---:|---:|
| 共享（现状） | 1275 | 495 | 7.817 |
| 拆成两个 | 1303 | 485 | 7.817 |

拆开反而多 28 个 LUT。共享是对的，产线不改。要复现，把 `fp32_mac_unit.v` 的
共享声明、二选一与规格化输出三处改成专用移位器即可。

### 4.5 给对齐移出位补粘滞位，实测判死

这一条来自精度那一侧：第十一章量出窗口在一种构造下会稳定地差 1 个 ULP，
因为被移出尺子的那部分里含着决定进位方向的信息。
修法是让移位器额外报出「移出去的位里有没有非零的」，并进粘滞位。

修法本身已经挑了便宜的写法。直接做要挂一个跟着移位量变化的 88 位掩码，
形状与桶形移位器同阶。但 `al_pre` 的低 `TW-48` 位恒零，
于是「移出去的位里有非零」等价于「尾随零个数小于被丢的位数」，
一个 48 位尾随零计数器加一个比较器就够了。实验副本由 `syn/mk_exp2.py` 生成。

| 档 | LUT | FF | CARRY | WNS |
|---|---:|---:|---:|---:|
| 现状 | 1275 | 495 | 89 | 7.817 |
| 补 sticky | 1469 | 500 | 90 | 7.817 |

多用 194 个 LUT（+15.2%），32 条 lane 就是 +6208。
这里有个不太舒服的巧合：三条白嫖一共省下 195 个 LUT，这个补丁刚好把它花光。

而且它买到的还不是正确性：一个布尔粘滞位恢复不了被丢残差的符号，
正负项抵消的时候，它可能把结果推向错误的方向。
所以不采纳，理由与替代方案（正解是把尺子加长到覆盖整个指数范围，让加法完全精确）
见[第十一章](11-定点窗口累加器的误差边界.md)第四节。

### 4.6 断言外提之后，lint 报语法错

本仓的 `ci_lint_local.sh` 把 `.vh` 也当独立源文件喂给 verilator，
而这份头文件里全是模块内部的语句，单独解析必然报 `syntax error, unexpected initial`。
`fp32_lat.vh` 没事，是因为它只有 `define`。

解法是把整份内容裹在 `FP32_MAC_ASSERT_INLINE` 里，宏没定义时它是空的。
这个解法自带假绿风险：谁将来漏了那行 `define`，断言会静默消失。
守门人是现成的，`tb_mac_win` 层次引用断言里的计数器，
把主文件的 `define` 注释掉，iverilog 当场报 `Unable to bind wire/reg/memory dut.mac_c1`，
五个计数器全报。已经这样注错验过一次。

### 4.7 六份窗口扫描日志里，一个 LUT 数都没有

做单 lane 对照时发现，此前那批扫描窗口宽度的实验日志里只有 FF 与乘法单元，
LUT 一栏全空。原因在 `syn/ooc.tcl` 抓结果的正则：
它要求名字后面直接跟空白，而 OOC 报告里那一行叫 `Slice LUTs*`，
带一个星号（「含 OOC 端口估计」的脚注标记），匹配不上，那一行被静默跳过。
而那批扫描的全部目的就是量面积。

正则已修（允许星号）。新写的 `ooc_mac.tcl` 干脆不解析文本，
直接数网表里的 `PRIMITIVE_GROUP`，报告格式再变也不会把判据变哑。

这是同一类问题的又一个实例：一个只会漏、不会报错的过滤器，
比没有过滤器更危险，它让人以为量过了。

顺带修掉的还有一处文档与代码不符：`fp32_mac_unit.v` 文件头 NOTE 6 写
「调用方须守三条契约」，而 C1 到 C5 是五条。

### 4.8 整机构建被系统静默杀掉

跑第二轮整机综合时踩到一个本机约束。这台机器 15.7 GB 内存，
Explore directive 的布局布线单进程峰值在 3.5 GB 以上，
叠上编辑器、浏览器与 WSL 之后物理内存只剩几百 MB，系统的低内存保护会把整个构建杀掉。
症状是进程在布局中途消失，日志停在某个 Phase 上，没有任何 ERROR 行，
很容易被当成还在跑。

加了 `Main/fpga/build_bit_lowmem.tcl`（先 `set_param general.maxThreads 4`
再 source 原脚本），慢一些但结果一致：那个参数只影响工具内部并行度，
不改布局布线的算法与 directive。

### 5.1 单 lane 离线综合

Vivado 2025.2，`xc7a200tfbg676-1`，20 ns 时钟，脚本 `syn/ooc_mac.tcl`。
OOC 档的乘法器落在 LUT 上（整机里走 DSP），所以绝对值高于整机的每 lane 数，只作相对对照。

|---|---:|---:|---:|---:|---:|

| 断言外提之后 | 1275 | 495 | 89 | 7.817 | 17 |

合计 LUT -195（-13.3%），FF -66（-11.8%），关键路径没有变差。

### 5.3 最差路径的落点

白嫖 D 之后整机 WNS 从 0.053 变成 0.054，几乎没动。要看的是落点：

| | 整机最差 setup 路径 | 阵列自己的最差 setup |
|---|---|---|
| 三条白嫖 | `n1_mag_reg[11]/CE`，slack 0.053，levels 0 | 同左，它就是整机最差 |
| 再加白嫖 D | `u_cpu` 的 TLB 到 EXE，slack 0.054，levels 34 | slack 1.550，levels 17 |

而 CPU 这一轮一个字都没改。
