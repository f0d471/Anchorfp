# FP32 比较器的三态编码与 NaN 语义

## 一、动机

### 靶子换了

加、减、乘做完之后重新拆了一遍账。浮点比较从原来占 3.3% 涨到 17.5%，
成了单项第一。

它的绝对成本没有变，31.56 拍还是 31.56 拍。占比上升是因为其他项都变快了：

```
   做之前                        做完加减乘之后

   乘法  ##########  45%          乘法  ###   18%
   加减  ######      28%          加减  ###   16%
   比较  #            3%          比较  ####  18%   <- 没变，但顶上来了
   其他  #####       24%          其他  ####  48%
```

这是逐项优化的常态：每做完一项，下一项的靶子由剩余分布决定，
所以每一轮都要重新拆账，不能按开工时的排序一路做下去。

## 二、为什么是这五步

### 比较不产生数值，它产生一个关系

前面三章的运算都是"两个浮点数进，一个浮点数出"，
所以都要经历规格化和舍入。比较不一样：

```
   加减乘   FP32, FP32  --->  FP32        要规格化、要舍入
   比较     FP32, FP32  --->  一个关系     不产生新的数
```

不产生新的数，就没有规格化，没有舍入，没有上下溢。
按[第一章](01-标量浮点协处理器接口设计.md)那条延迟准则，
这个单元应该做成 1 拍。

### 电路的部分几乎是白送的

IEEE 754 的字段顺序是符号、阶码、尾数，从高位到低位，
而且阶码是偏置编码的无符号数：

```
   +-+--------+-----------------------+
   |s|   e    |          f            |
   +-+--------+-----------------------+
      高位 <-------------------- 低位

   e 大的数绝对值就大；e 相同时 f 大的绝对值就大
   => 位序天然就是数值序
```

所以同号的两个浮点数，直接当整数比大小，结果跟按浮点比一样。
比较主体是一个整数比较器。

### 工作量全在语义对齐上

真正要做的事情不是"比大小"，是把 IEEE 的序关系映射到 libgcc 的 ABI 上。
两边有三处对不上，每一处生出一步：

```
   对不上之处 1：零有两个位模式
       +0 = 0x00000000    -0 = 0x80000000
       位不同，但 IEEE 规定它们相等
       直接当整数比会得出 -0 < +0
       => 要单独判

   对不上之处 2：NaN 与任何数都不可比
       IEEE 说 NaN 参与的比较是"无序"，四种关系都不成立
       而 ABI 只有三个返回值（负 / 零 / 正），没有第四种
       => 要决定无序时返回哪一个

   对不上之处 3：六个比较符号方向相反
       lt/le/eq/ne 遇到 NaN 要返回正值
       gt/ge       遇到 NaN 要返回负值
       => 硬件要知道调用方属于哪一族
```

再加上返回值使用三态码的格式和 FTZ 契约同步，
一共五步：

```
   一  比较主体      异号看符号位，同号比低 31 位整数值
   二  处理零        正负零判相等
   三  返回三态码    对上 libgcc 的 ABI
   四  处理 NaN 方向  六个符号分两族
   五  FTZ 规整      跟加法器乘法器同一套契约
```

## 三、每一步做了什么

### 3.1 比较主体和零

三种情况分开处理：

```
   异号        a 为负 => a 小              只看符号位
               +-+---------------+
               |1|      ...      |   a
               +-+---------------+
               |0|      ...      |   b     a < b
               +-+---------------+

   同号为正    直接比低 31 位              位序 = 数值序
               a[30:0] < b[30:0]  =>  a < b

   同号为负    比低 31 位再取反            绝对值大的负数反而小
               a[30:0] < b[30:0]  =>  a > b

   两个都是零  判相等                      +0 和 -0 位不同但数值相等
               否则会走进"异号"那一支，判成 -0 < +0
```

零那一支必须提前判掉，否则它会被"异号"分支接管，给出错误答案。

### 3.2 返回三态码

要顶替的是 libgcc 的 `__ltsf2` / `__lesf2` / `__gtsf2` / `__gesf2` /
`__eqsf2` / `__nesf2`。这一族函数的 ABI 返回的不是布尔，是三态整数：

```
   a < b   ->  返回负值
   a == b  ->  返回 0
   a > b   ->  返回正值

   调用方拿到之后自己再跟 0 比一次：
       a < b   编译成   call __ltsf2; 结果 < 0 则跳转
       a > b   编译成   call __gtsf2; 结果 > 0 则跳转
```

所以硬件也返回三态。

当时担心过一件事：返回三态意味着调用方还要多做一次整数比较和分支，
会不会把省下来的拍数抵消掉。板上直接量了一次，
探针的循环体写的就是 `(a < b) ? 1 : 0`，调用方的整数比较和分支都算在里面，
结果是 5.99 拍，跟 `__addsf3` 一样。担心不成立。

### 3.3 NaN 的方向

调用方对返回值的判断方向不同，而 NaN 参与的任何比较都应该是假。
要让两族都判成"条件不成立"，返回值必须往相反的方向给：

```
                        硬件返回      调用方的判断        结果
   lt 族遇到 NaN          +1          +1 < 0 ？ 否       条件不成立  对
   gt 族遇到 NaN          -1          -1 > 0 ？ 否       条件不成立  对

   如果两族都返回 +1：
   gt 族遇到 NaN          +1          +1 > 0 ？ 是       条件成立    错
```

所以硬件必须知道调用方属于哪一族。

### 3.4 六个符号只占一个 op

如果给六个符号各分一个 op，会占掉编码空间的 3/8
（[第一章](01-标量浮点协处理器接口设计.md)把空间从 4 扩到了 16）。
而六个符号的差别只有 NaN 时的方向，一位就够。

那一位走立即数通道。这条通道 CPU 一直在传，之前一直标着未使用：

```
   +-------+--------+-------+
   |  op   |  imm   | 操作数 |
   +-------+--------+-------+
       |       |
       |       +-- imm[0] = 0  ->  lt/le/eq/ne 族
       |           imm[0] = 1  ->  gt/ge 族
       +---------- 六个符号共用同一个 op
```

零成本。同样的手法后来在转换指令上又用了一次，
`imm[0]` 选方向、`imm[1]` 选有无符号，i2f 和 f2i 合并成一个 op
（[第六章](06-FP32与整数转换单元实现.md)）。

### 3.5 FTZ 规整

入口把 denormal 规整成同符号的零，跟[第四章](04-FP32加乘单元的FTZ语义实现.md)同一套契约。这一步不影响性能，只保证四个消费者对同一个数给出同一个答案。

## 四、遇到的问题

### 4.1 家族位接反，常规值一条都验不出来

**第一现场。** 家族位如果接反，用常规浮点值做激励，一条用例都不会失败。

**解读。** 原因是对有序的输入，两族返回的是同一个值：

```
                   lt 族返回    gt 族返回    一样吗
   a < b             -1           -1         一样
   a == b             0            0         一样
   a > b             +1           +1         一样
   任一是 NaN        +1           -1         不一样  <-- 只有这里
```

方向的差别只在 NaN 上体现，而 NaN 不会出现在随机浮点激励里，
除非专门构造。

这跟[第三章](03-FP32加法器的三级流水实现.md) 4.2 的零符号是同一类问题：
一个控制位只在某个窄输入子集上有可观测效应，
不覆盖那个子集的判据对它的鉴别力为零。

**修法。** 板上自检里补四条 NaN 用例：

```
   qNaN vs 1.0        lt 族应返回 +1，gt 族应返回 -1
   1.0  vs qNaN       同上，验 NaN 在第二个操作数位置
   qNaN vs qNaN       两边都是 NaN
   sNaN vs 1.0        验信号 NaN 走同一条路
```

再加四条 FTZ 的，把 FTZ 契约也钉住：

```
   dmin  vs +0        应当相等   （denormal 被当成零）
   -dmin vs +0        应当相等
   dmax  vs 1.0       应当小于
   dmin  vs -1.0      应当大于   （denormal 变成 +0，大于 -1.0）
```

**方法。** 写定向用例的时候先想清楚：如果实现偷懒或者接反，
会在哪一类输入上露馅。然后确保那一类输入在用例里。

### 4.2 板上判据自己写错了

**第一现场。** 单价探针 `fpmark` 里的 fcmp 那条判据报：

```
fcmp: 240/256 mismatch
```

**解读。** 失配 240，总数 256，匹配的只有 16 条。

16 这个数很可疑。256 = 16×16，说明激励是一个 16×16 的组合矩阵；
匹配的正好是 16 条，等于矩阵的一条对角线的长度：

```
        b0  b1  b2  ...  b15
   a0   ok  X   X        X
   a1   X   ok  X        X
   a2   X   X   ok       X
   ...              ok
   a15  X   X   X        ok
        ^
   匹配的全在对角线上，也就是 a == b 的那 16 组
```

一个真正的实现缺陷很少会精确地放过一个有结构的子集。
匹配集有结构，说明失配是系统性的，而且跟"相等"这个关系有关。

**定位。** 硬件返回三态整数，判据把它当布尔比：

```
   关系      硬件返回    判据期望   符合吗
   a < b       -1          1        不符
   a > b       +1          0        不符
   a == b       0          0        符合    <-- 对角线
```

**结论。** 硬件没错，判据错了。

**方法。** 失配数等于"总数减去某个可解释的子集"的时候，先怀疑判据。

**修法与结果。** 判据改成按三态对照，不再当布尔用：

```c
int hw = lacc_fcmp_lt(a, b);
int lt = (a < b), gt = (a > b);
if ((hw < 0) != lt || (hw > 0) != gt) ncmp++;
```

改完之后板上重烧，`fpmark` 七条判据全过，fcmp 那条从 240/256 失配变成 0 失配。
硬件一个字没改——从头到尾错的只有判据。

## 五、结果

| | 软件 libgcc | 硬件 |
|---|---:|---:|
| `__ltsf2` | 31.56 拍 | 5.99 拍 |

geometry 那一级从 1,662 ms 降到 1,461 ms，少了 12.1%。

这个工作点之后 `fcmp` 的占比从 17.5% 降到 3.8%，从第一掉到第五。
段级数据对得上：以裁剪和比较为主的 `radius` 段降了 31.2%，
而纯乘加的 `cov3d` / `cov2d` 只降了 2 到 3 个百分点。

### 顺便裁掉的一件事

同期考虑过要不要加 `FMIN` / `FMAX`。查了一遍全仓，
`fminf` / `fmaxf` 零命中，也没有 `a < b ? a : b` 这种写法，
实际全是 `if (x > 40.0f) x = 40.0f;` 这类钳位，共 10 处。

这些钳位编译出来是一次比较加一条条件分支，比较那部分已经被 `fcmp` 覆盖。
一条 `FMINMAX` 能省的只有那个分支，一两拍，而且要改被测代码才用得上。
收益不到 0.5%，不做，op 10 到 12 保持预留。
