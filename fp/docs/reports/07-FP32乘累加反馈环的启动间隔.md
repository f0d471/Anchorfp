# FP32 乘累加反馈环的启动间隔

本章记录乘累加单元的第一种结构：由乘法器、加法器与累加寄存器首尾相接成反馈环。
第 08 章把这个结构整体替换为定点窗口累加器，本仓的 RTL 只包含替换之后的形态。
本章的分析是理解第 08 章为什么要换、换掉了什么的前提。

## 一、动机

矩阵乘、卷积与投影这类负载的底层是长点积：`Σ aᵢ × bᵢ`。调用方需要一个乘累加单元，
一项一项地喂入 `(a, b)`，在最后一项之后拿到和。多条点积可以并行，于是一个阵列里会例化几十份。

前面几章的单元都是单向流水线，第 k 笔与第 k+1 笔互不相干，可以每拍喂一笔。
乘累加不是这个形状，它把加法器的输出接回了加法器自己的输入。
这一章回答的问题是：接成反馈环之后，隔多久才能喂下一项。

## 二、为什么这一章的问题与前面不同

### 前面几章没有反馈

```text
   输入 ---> [级1] ---> [级2] ---> [级3] ---> 输出

   第 k 笔和第 k+1 笔互不相干，可以一拍接一拍地喂
```

延迟长一点只是结果晚出来，吞吐不受影响。

### 反馈把延迟变成了依赖距离

```text
   积 ---> [ 加法器 ] ---> [ acc ]
                ^             |
                +-------------+
                  反馈
```

一旦成环，第 k 项要读的 acc 是第 k-1 项写进去的。延迟不再只是"结果晚出来"，
而是"下一项要等多久才能开始"。这个间隔叫启动间隔（initiation interval），下文记作 Pace。

### 步骤由这个问题生出来

```text
   一  定结构          一个乘法器、一个加法器、一个累加器
   二  定 Pace         算出隔多久能喂一项                   <- 反馈带来的核心问题
   三  末项标记随行     "最后一项"在输入端产生、在输出端使用  <- 流水带来的连带问题
```

## 三、每一步做了什么

### 3.1 结构

```text
   a ---+
        | [ 乘法器 ] --- 积 ---+
   b ---+                      |
                               v
                          [ 加法器 ] --- 和 ---+
                               ^                |
                               |                v
                               +----------- [ acc ]

   另有一条加载通路，可以把外部的部分和直接写进 acc
```

乘法器与加法器就是第 02、03 章的单元，属于常规实现。

### 3.2 定 Pace

加法器是 3 级流水，不能每拍喂一个积：

```text
   若每拍喂一个（Pace = 1）

   拍号      0     1     2     3     4
   积 0    进入
   积 1          进入
   积 2                进入
   acc 更新                    ^ 积 0 的和这时候才写进 acc

   积 1 在拍 1 就读了 acc，那时积 0 的和还没写进去，读到的是过期值
```

解决办法是降速：每隔 Pace 拍喂一个积，同一时刻反馈环里只有一个加法在飞。
Pace 该取几，由第四节确定。

Pace 是调用方要遵守的约定：喂快了，单元不反压也不报错。所以它与各单元的延迟放在一起，
写在 `fp32_lat.vh` 里，并且写成由加法器延迟推出的表达式，加法器改级数时调度方与测试台一起跟着变。

### 3.3 用交错累加器恢复每拍一项

单累加器的吞吐只有 1/Pace。要恢复每拍一项，可以摆 Pace 个累加器交错使用：
第 k 项进第 `k mod Pace` 个，喂完之后再用同一个加法器把它们两两归约成一个和。

这个办法有效，但付出一整条链的代价：累加器成了数组，多路选择器进入环内；
需要一棵归约树与一份归约控制，每份例化各一套；求和次序变成累加器个数的函数，
金标准必须复刻这个次序；每一项乘积仍然各自舍入一次，误差随项数累积。
这条链是第 08 章的出发点。

### 3.4 末项标记随数据走

"这是最后一项"这个信息在输入端产生，要在输出端使用，中间隔着乘法器的 2 拍与加法器的 3 拍：

```text
   数据   积 ---> [乘法器 2 拍] ---> [加法器 3 拍] ---> 和
   控制   last -> [ 移 2 拍 ] ----> [ 移 3 拍 ] ----> 此时才用

          两条链的级数必须一样，否则错位
```

控制链深度同样取自 `fp32_lat.vh` 的 `FP32_MUL_LAT` 与 `FP32_ADD_LAT`，与计算单元的流水级数是同一个数，
只在一处定义。这种影子流水的前提是没有反压，有反压就要配握手信号。

## 四、遇到的问题

### 4.1 Pace 取 3，结果少一半

第一现场。直觉答案是 Pace 等于加法器级数 3。按这个数实现，跑一个四项点积，四项全是 `1.0 × 1.0`，期望 4.0：

```text
MISMATCH dot=0: got=40000000 exp=40800000 ulp=4194304
==== fp32_mac_unit (降速单累加) vs 顺序点积 IEEE 金标准 ====
total=1  bad=1  maxulp=4194304
FAIL
```

解读。`40000000` 是 2.0，`40800000` 是 4.0，结果正好是期望的一半：

```text
   若是加法器算错      四个 1.0 相加不会正好得到 2.0
   若是溢出或 NaN      会得到 Inf 或 qNaN
   若是随机时序问题     每次运行结果不同

   得到整整齐齐的一半 => 四项里只有两项被累加进去，而且丢得有规律
```

所以要查的是节拍，不是数值通路。

定位。写一个逐拍打印的调试测试台，把"积就绪""加法完成""acc 当前值"三个信号逐拍打出来：

```text
   拍号       ...    k     k+1   ...
   积就绪            ^
   加法完成          ^                <- 两个信号落在同一拍
   acc 的值        旧值   新值

   第 k 个积的加法在这一拍读 acc（读到的是当前值，即旧值）
   而 acc 要到这一拍的末沿才被第 k-1 个积更新
```

画成环路：

```text
   acc ---> [ 加法器 3 级 ] ---> [ acc 寄存 1 级 ] ---> acc
    ^                                                   |
    +---------------------------------------------------+

   一圈走过的级数 = 3 + 1 = 4
```

根因与修法。环路里除了加法器的 3 级，还串着累加寄存器自己那一级，环路延迟是 `L + 1`。
Pace 改为 4，四项点积得 4.0。

原判据为什么没有覆盖到它：当时没有判据约束 Pace 的下界。计算反馈环的启动间隔时，
不能只数运算单元的级数，目的寄存器本身也在环里。

## 五、结果

这一形态的测试台比较的是逐位相同，而不是数值接近：硬件结果必须与"按顺序逐项用 IEEE 加法累加"
的结果逐位相同。浮点加法不满足结合律，`(a + b) + c` 可能不等于 `a + (b + c)`，
累加顺序本身是结果的一部分，这条判据同时锁定了硬件的累加顺序。3000 个点积，0 ULP。

Pace 本身从两头夹住：按 Pace 拍喂入，结果与金标准逐位相同；按 Pace-1 拍喂入，结果必须不同。
只测前一条，Pace 填成 100 同样能通过；后一条给出的是"这个数不能再小"。

这一形态的测试台随结构一起替换，本仓不再包含。

## 六、还欠什么

反馈环长 4 拍，要恢复每拍一项就必须付出 3.3 节那一整条链的代价，并且每一项乘积各自舍入一次。
这两件事由第 08 章处理。
