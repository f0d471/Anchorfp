# 标量浮点单元的接口与契约

这是 fp 系列的第一章，讲骨架：为什么要做 FP32 硬件单元，这些单元以什么形状交给调用方，
延迟怎样记录与约束，数值上做到什么程度算做对。后面每一章落地一个具体单元。

## 一、动机

### 软件浮点的代价

在 FPGA 上搭加速器，旁边的控制核多半没有浮点单元。C 代码里写 `a * b`，
编译器只能发出一次函数调用，由软件浮点库用整数指令把浮点乘法模拟一遍。
在一颗无浮点单元的 32 位 RISC 软核上用紧循环探针测量，一次 FP32 乘法约 131 个周期，
那个库函数里大约有 240 条整数指令。131 个周期的原因是没有硬件。

### 做独立单元，不改内核

让 `a * b` 变快的第一条路，是给 CPU 加标准浮点扩展：改译码，加浮点寄存器堆，
处理浮点异常与状态寄存器，在上下文切换中保存浮点状态，还要改工具链让编译器发出这些指令。
这些工作里只有运算单元本身与"把乘法算快"有关，其余都是把它接进指令集体系的配套工作，
而且会动到内核里已经验证过的取指、译码、转发与异常通路。

所以本系列的做法是把加、减、乘、比较、转换与倒数做成独立的数据通路模块，
由调用方例化：可以是 CPU 旁挂的协处理器接口，可以是加速器里的向量化执行单元，
也可以是多条并行的点积阵列。单元本身不关心调用方是谁。

### 两种调用方式带来的约束

调用方分两种。一种是阻塞式：发出请求后停下来等结果，一次只有一条请求在单元里，
此时单元延迟就是这次运算的价格。另一种是流水式：每拍发起一条，吞吐由发起间隔决定。

```text
   阻塞式调用方
   ... -- [ 发请求 ] ... 等 ... 等 ... [ 收结果 ] -- ...
                    |<--- 单元延迟 --->|
                    调用方在这段时间里不做别的事
```

在阻塞式调用方后面，加法器多切一级流水，每一次浮点加法就多付一拍，没有别的运算能填进这个空档。
这与一般流水线设计的习惯相反：平常切流水是为了提频率，延迟变长而吞吐不变；
在阻塞式调用方后面，延迟变长就是单价变贵。

由此得到一条贯穿后面所有章节的准则：**每个单元的延迟压到能满足时序的最小值**。
要更高吞吐，就多例化几份，而不是把单个单元切深。后果有三处：比较与转换只有 1 拍；
加法器切三级，因为前导零计数在 20 ns 里放不下；分发层的五个出口延迟各不相同，不做延迟对齐。

### 这套单元是给谁用的

延迟准则只是约束的一半。另一半是数值上做到什么程度算做对，
这一条必须在写第一行 RTL 之前定下来，否则后面每一章的判据全绿都没有依据：
判据只比对了它拿到的那份激励，而那份激励该覆盖什么，需要先有规定。

这是一套给边缘 FPGA 上的 AI 加速器用的 FP32 算术单元，不是通用 IEEE FPU。三个约束决定其余一切：

- 负载是神经网络推理与三维渲染。数据动态范围窄，输出端有量化台阶或取最大值，异常标志没有消费者。
- 平台是 Artix-7 一类器件，50 MHz，逻辑资源以万计。流水级数按一拍装得下来切。
- 消费者包括软件浮点例程的替换、向量化调用与多条并行的阵列。同一批单元多处复用，
  替换语义是核心：使用者的 C 代码不改，换一个实现，结果在共同定义域上必须逐位相同。

不在定位之内的使用者：需要位精确可复现的科学计算，需要非规格化数的信号处理，
需要异常与陷阱的运行时。

### 判断偏离的标准

定位划出范围，还需要一把尺子判断范围内的每一条偏离是取舍还是缺陷。
这把尺子看的是误差有没有规则，而不是误差大不大。

可操作的说法：一条偏离能不能用一句不带"通常""大多数"的话说清楚，
并且使用者据此能判断自己是否受影响。能，就是取舍；不能，就是缺陷。

用最大的一条偏离检验它：非规格化数一律按零处理（FTZ）。这条偏离在非规格化区间的
相对误差是 100%，比任何 1 ULP 都大。它可以接受，是因为它是一条规则：边界清晰、全域一致，
使用者能在自己那一侧判断数据是否落在这个区间里。反过来，"某些输入碰巧差一点"
哪怕误差再小也不可接受，因为使用者无法推理。

这把尺子有两个推论，后面各有一章用到：免责声明不如一个仍然成立的界（第 08 章）；
一条说不清楚的规则本身就是缺陷，哪怕每一次计算都是对的（第 02 章 4.5 节）。

## 二、为什么是这几步

在任何一个算术公式之前，骨架要先定下五件事：

1. **单元接口。** 每个单元用什么端口接收一条运算、交出一个结果、作废在飞的运算。
2. **分发层。** 需要一个入口按操作码把输入送到对应单元，并决定是否对齐各单元的延迟。
3. **延迟常数。** 调用方按延迟搭建对齐流水，延迟必须有唯一定义处，并且是实测量。
4. **操作码编码。** 编码属于集成方的指令体系，必须与计算单元解耦，只在一处定义。
5. **数值契约与回归入口。** 承诺分档写清楚，并给出能直接接门禁的回归脚本。

前四件决定单元能被怎样调用，第五件决定单元的行为能不能被说清楚、被检查。
这五件与"浮点怎么算"无关，后面每一章的计算单元都挂在这层骨架上。

## 三、每一步做了什么

### 3.1 单元接口

五个计算单元采用同一种接口：`in_valid` 与操作数同拍给出，单拍脉冲即可，操作数不必保持；
`out_valid` 与结果同拍拉高一拍；`flush` 作废所有在飞运算。没有反压。

valid 链与数据逐级同深度，`flush` 只清 valid 链：

```verilog
reg v1, v2;
always @(posedge clk) begin
    if (!rst_n || flush) {v1, v2, out_valid} <= 3'b0;
    else                 {v1, v2, out_valid} <= {in_valid, v1, v2};
end
```

作废一条在飞运算等于让它的 valid 位消失，数据继续往下走，`out_valid` 为低时结果没有意义。
这个写法的前提是没有反压，有反压的通路须改由 ready 参与握手。

五个单元的输出都是寄存器，组合逻辑在输出寄存器前收口，跨模块路径两端均落在寄存器上。

### 3.2 分发层

`fp32_fpu_top` 按操作码把一路输入送给五个计算单元，本层不含算术逻辑：

```text
                        fpu_op
                          |
   fpu_a / fpu_b ---> [ 译码 ] ---+-------+-------+-------+-------+
                                  |       |       |       |       |
                                  v       v       v       v       v
                                加减     乘     比较    转换    倒数
                                3 拍    2 拍    1 拍    1 拍    5 拍
                                  |       |       |       |       |
                              五对 valid / data 各自引出，由调用方按操作码选择
```

减法复用加法器，分发层把第二个操作数的符号位取反。比较器的族位与转换器的方向位、
有无符号位由 `fpu_imm` 的低位给出。

五个出口的延迟不同，分发层不做延迟对齐。对齐意味着给短延迟的出口补寄存器，
让它们都等到最慢那一个的节拍：

```text
   不对齐（采用）              对齐（未采用）

   比较  |=|                   比较  |=|----|
   乘    |==|                  乘    |==|---|
   倒数  |=====|               倒数  |=====|
         各按各的延迟出            全部拉齐到 5 拍
```

在阻塞式调用方后面延迟就是单价，对齐会把比较的成本变成原来的五倍。
另一个理由是可观测性：在某个出口上额外加的寄存器在模块外部看不见，
调用方若直接例化同一计算单元并按单元延迟配置对齐流水，会产生数据错位。

### 3.3 延迟常数

单元延迟定义为：`in_valid` 被采样的时钟沿记为 T，`out_valid` 拉高的时钟沿为 T+N。

`fp32_lat.vh` 是唯一定义处：

```verilog
`define FP32_ADD_LAT   3
`define FP32_MUL_LAT   2
`define FP32_CMP_LAT   1
`define FP32_CVT_LAT   1
`define FP32_RECIP_LAT 5
```

这些值是仿真实测量，不由流水级数推算。约束分两层：

- 例化期：分发层与乘累加单元里的条件 generate 例化不存在的模块，约束常数的取值范围与相互关系。
  这一层不能约束常数与实际拍数是否一致。
- 仿真期：`tb_fp_lat.v` 逐单元实测 `in_valid` 到 `out_valid` 的拍数，与各宏比对。

修改任一单元的流水级数后，`tb_fp_lat.v` 会报错。正确的处理是重测并更新 `fp32_lat.vh`，
不得修改判据以匹配实测值。调用方搭建对齐流水时必须引用这些宏，不得另写数值。

测试台若从采样沿之后的第一个沿开始计数，量出的值比宏小 1。比较两个延迟数之前，
先确认两者的计数起点相同。

### 3.4 操作码编码

`fp32_ops.vh` 定义操作码域宽度与六条运算的编码，以及"哪些编码走本目录单元"的归类宏。
编码值本身没有数值含义，集成方按自己的指令编码修改这一个文件即可，五个计算单元与编码无关。
例化方传入的 `OpWidth` 与编码表的宽度由分发层在例化期检查。

### 3.5 数值契约

按 1.5 节的尺子，把承诺切成三档，顺序就是优先级。

**A 档，不可协商**，违反即缺陷，不计面积：

1. 加、减、乘、比较、转换在定义域内相对无限精度正确舍入，即 0 ULP；
2. 在共同定义域上与软件浮点例程逐位一致，共同定义域为输入非 denormal、
   且无限精度结果按 B 档的规则判定为非 tiny；
3. 同一运算在标量与向量路径上逐位相同，同一输入永远同一输出；
4. 比较器对非 NaN 输入给出真实序关系；
5. 特殊值不产生无意义的结果，Inf、NaN、零的传播规则确定；
6. 能在编译期检查的违约必须在编译期检查；
7. 说明书里的每一个精度数字都要有验过的出处，写明是在什么范围上测的。

**B 档，明示偏离**，写进契约，使用者可预期：

- 输入 DAZ：算术输入指数字段为 0 的位图按同符号零解释；
- 输出 FTZ：结果判定为 tiny 时写同符号零，tiny 在舍入之后判定（第 02 章 4.5 节）；
- 只实现就近舍入到偶数；浮点到整数的转换按定义向零截断；
- 不产生异常标志；
- 算术结果保证是 quiet NaN，不承诺载荷与符号，倒数单元对 NaN 原样透传；
- 倒数单元是显式近似，误差不超过 4 ULP，不用于替换除法；
- 标量路径没有融合乘加，`a * b + c` 是两次舍入；
- 乘累加单元的误差由一条不等式约束（第 08 章）。

**C 档，性能、面积与功耗**，排在前两档之后。

这个顺序意味着：一条偏离若不在前两档允许的范围内，就应当实现它；
明确舍弃的部分，例如非规格化数的数值通路，不再为它做任何工程。

FTZ 是标准允许的取舍：x86 的 SSE 有 FTZ 与 DAZ 控制位，ARM 有 FZ 控制位，
资源受限的嵌入式 FPU 常常只有这一种模式。代价是绝对值小于约 1.2e-38 的中间结果变成 0，
对神经网络推理与三维渲染没有意义。收益是硬件里省掉前导零计数、变长移位与阶码修正这一整条通路。

### 3.6 回归入口

`sim/` 下有三个入口脚本：`run_all.sh` 跑全部计算单元的金标准对拍与延迟检查，
`run_mac_audit.sh` 跑乘累加单元的定向反例、注错与误差报告，`lint.sh` 对每个模块做结构检查。

三个脚本全绿返回 0，任何一条判据不过返回 1，可以直接接门禁。
判定一份仿真输出要求两件事同时成立：没有失败标记，并且至少有一条通过标记，
后一条保证测试台什么都没打印时也判为失败。

## 四、遇到的问题

### 4.1 延迟记录与实测不符

第一现场。延迟原先只写在注释与文档表格里。补了实测测试台之后第一次运行，
倒数单元报出不符：

```text
FAIL: FRECIP 延迟实测 6 拍，记录为 3 拍
```

以上按当时的对账记录还原。

解读。倒数单元在补上牛顿迭代之后多了三级流水，记录从未更新。
其余四个单元的记录与实测一致，说明这不是计数口径的系统性偏移，而是某一次改动没有同步。

定位。延迟只以文字形式存在，没有任何东西检查它。改流水级数的人不会想起去改文字，
而依据这个数搭建对齐流水的调用方会因此错位。

根因与修法。延迟收进 `fp32_lat.vh`，值取实测量；`tb_fp_lat.v` 断言实测值等于宏，
断言方向是"实测必须等于宏"，反过来写会自动接受任何改动；分发层与乘累加单元另加例化期检查。

原判据为什么没有覆盖到它：没有判据。写在注释里的事实断言，只有在测试台断言它的地方才靠得住。

### 4.2 回归脚本永远返回成功

第一现场。两个入口脚本在任何一条判据失败时都返回 0：

- 一个的尾部固定 `exit 0`，失败计数只打印不返回；
- 另一个的判定经过一个 `grep` 管道，脚本的退出码是 `grep` 的，不是仿真的。

解读。判据都在，而且各自正确，但报告层把它们的结论吞掉了。
用这样的脚本当门禁，等于没有门禁；而前面每一章声称全绿，出处正是这两个脚本。

根因与修法。报告层也要有判据。两个脚本改为由失败计数决定退出码，以 `[ "$FAIL" -eq 0 ]` 收尾，
并各做一次注错：把一档判据改坏、让一个测试台编译失败，脚本必须返回非零；全绿必须返回零。

这一条的优先级排在所有精度问题之前：判据的可信度不先修好，后面每一条验收都可能是假的，
包括验收"修好了假绿"这件事本身。

原判据为什么没有覆盖到它：报告层自己没有判据。

### 4.3 语义边界放在了调用方

第一现场。加法与乘法单元最初不处理 denormal，行为与 IEEE 不一致。
调用方为了把这类输入挡在硬件之外，在软件包装里先做四项分类：

```text
   调用 加法
        |
        v
   +----------------------------+
   | 软件包装                    |
   |   操作数是 denormal 吗？    |
   |   操作数是 Inf 吗？         |
   |   两个 Inf 异号吗？         |
   |   结果会下溢到 denormal 吗？ |
   +----------------------------+
        |                    |
   四项都不命中            任一项命中
        |                    |
        v                    v
     硬件单元              软件浮点
```

在同一颗软核上用紧循环探针测量，包装的总开销是裸硬件调用的两倍以上，
多出来的全部是这四项分类。

解读。分类本身是必要的，位置错了。它判断的是"这个输入硬件能不能算"，
这件事硬件在拆包那一拍就能判完，放在软件里要花十几条整数指令。

根因与修法。把语义边界挪进硬件：单元在拆包时按 DAZ 规整输入，在组装时按 FTZ 规整输出，
对所有输入给出确定的结果，调用方的包装只剩一次调用。
这一条改的是契约，算术本身不变，各单元的具体改动见第 02、03、04 章。
四个消费者（加法、乘法、比较与乘累加）从此对同一个位图给出同一种解释。

原判据为什么没有覆盖到它：单元级判据只检查单元对它接受的输入是否算对，不检查调用方为了让它
"接受"付出了多少代价。

| 单元 | 延迟 | LUT | FF | DSP48 | BRAM | 20 ns 下 WNS |
|---|---:|---:|---:|---:|---:|---:|
